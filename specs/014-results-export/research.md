## R1 — The manifest in the loss repository is the export record; the Workbench keeps no export table (T-03, T-08, T-12)

**Decision**: An export is a UUID `export_id` generated by the route on
submit. One `stage.rwb_loss_result_manifest` row per selected analysis in the
loss repository carries it, together with `requested_by_email` and
`requested_at`. The rows are written before any job runs and hold every value
the load uses; workers and the load procedure only update status, archive
path, counts, and `data_id`. The Workbench holds `rwb_job` and `irp_job` rows
that reference `export_id` (`rwb_job.requestor_id` of the submit job, the new
`irp_job.export_id` column), and no export table.

**Rationale**:

- AGENTS.md rule 8 (approved plans are immutable): the manifest row is the
  plan the analyst approved. Writing it at submit and never recomputing it
  (spec FR-006) is what the rule asks for.
- CIC's DBA must trace a loaded `Data` row without a Workbench login (spec
  FR-023; note 25 D7). A batch ID and requester email in the same database
  as `Data` does that; a Workbench table would not be visible to them.
- Note 25 §3.3 (O25-1) framed the choice as "one of those two tables should
  not exist": `analysis_result_meta`/`result_export` in `docs/DATA_MODEL.md`
  §9, or the manifest in the repository. The manifest wins because the
  enrichment join and the load procedure need the analysis-level facts on
  the same server as the stage rows and the lookup (note 25 D2, D3).
  `analysis_result_meta` and `result_export` exist only as a diagram in §9;
  no migration or code names them, so removing them costs nothing.
- `export_id` follows the `irp_analysis.execution_id` precedent: an ID that
  groups rows without a table of its own. `rwb_job.requestor_id` has no
  foreign key, so it can hold the UUID.

**Alternatives considered**:

- *A Workbench `result_export` table plus a repository manifest* — the same
  facts in two databases with no transaction across them; every status page
  would join across servers. Rejected (note 25 O25-1).
- *Manifest in the Workbench only, stage rows in the repository* — the load
  procedure could not read the header values it copies into `Data`, and the
  client team could not run a load without the Workbench (spec FR-022).
  Rejected.

## R2 — One data set per analysis per perspective, enforced by a unique index (T-09)

**Decision**: `stage.rwb_loss_result_manifest` is unique on
(`irp_app_analysis_id`, `perspective_code`). The form marks an analysis
exported when a row exists for the chosen perspective in any status; the
route re-runs the check and rejects the whole submission naming the analysis;
the index catches the concurrent case. The route inserts all manifest rows of
one export in one transaction so the second submitter gets none of its rows
written.

**Rationale**:

- `dbo.Data` has no primary key and no unique constraint on `DataID`
  (`cic-reference/DataTableDDL.sql`); `RMSELT.DataID` and
  `RMS_HistoricalRDS.DataID` are nullable `INT` with no foreign key
  (`cic-reference/ELT_RepositoryDDL.sql`). Nothing in CIC's tables would
  reject a second header row, so the Workbench owns the guarantee (spec
  non-negotiable 1, SC-004).
- The key is the pair CIC can see in `Data` (`AnalysisID`, `Perspective`),
  not the Workbench UUID, so the same Risk Modeler analysis registered twice
  in the Workbench still gets one data set.
- User decision 2026-09-09 (spec P-09): no override until O-01 decides
  whether CIC ever reloads.

**Alternatives considered**:

- *Warn and allow a repeat export* (the 2026-09-03 assumption) — produces a
  second `Data` row nothing rejects. Rejected 2026-09-09.
- *A key on `irp_analysis_id`* — two Workbench rows for one Risk Modeler
  analysis would load twice. Rejected.

## R3 — The load is a stored procedure that claims the manifest row inside its own transaction (T-05, T-17, T-18)

**Decision**: `stage.usp_load_elt_result @manifest_id` runs the lookup
assertion, classification, the two corrections, the `Data` insert, and the
two loss-table inserts in one transaction whose first statement claims the
manifest row (`load_status = 'loading'` from `stage_status = 'staged'` and
`load_status IN ('pending','failed')`, raising when zero rows are claimed).
The worker calls it through a new `db.execute_procedure(name, params,
connection)` that opens the connection with
`execution_options(isolation_level="AUTOCOMMIT")`. The procedure raises on
entry when `@@TRANCOUNT > 0`, rolls back in `CATCH` when `XACT_STATE() <> 0`,
writes `failed` after the rollback, and rethrows. The worker also stamps
`failed` when the call raises before the procedure could write, and does
nothing when the row already reads `loaded`.

Two sessions loading the same manifest at once: the second blocks on the
claim row's lock until the first commits or rolls back, then re-evaluates
the predicate. After a commit it reads `loaded` and raises 50001 naming the
data ID; after a rollback it reads `failed` and performs the load itself.
The "manifest {id} is loading" message needs a row persisted as `loading`,
which the rollback undoes, so it is unreachable in practice and kept only for
completeness. Review finding 2026-09-10.

**Rationale**:

- Spec FR-022: the client team can load a staged analysis from SQL Server
  Management Studio without the Workbench. Only server-side code does that.
  User decision 2026-09-07 replaced the repo-owned SQL script the worker
  would have run.
- `dbo.Data.DataID` is `IDENTITY(1,1)` (`DataTableDDL.sql`), not a
  `SEQUENCE`; the ID exists only after the insert. The row claim, not a
  reserved ID, is the duplicate guard (user 2026-09-09; replaces note 23 D6).
- `db.execute` runs on `engine.connect()` and `db.execute_command` on
  `engine.begin()` (`db/execute.py:34`, `:102`); the second commits on
  success and rolls back on exception. Under either, the procedure's
  `BEGIN TRANSACTION` nests (`@@TRANCOUNT` 1→2) and its `COMMIT` only
  decrements, so a load would be rolled back after reporting success, or
  the `CATCH` write lost. Nothing in `db/` uses autocommit today; the only
  precedent is `infra/scripts/bootstrap_db.py:40`, which needs it for
  `CREATE DATABASE`.
- `XACT_STATE()` rather than `@@TRANCOUNT`: a doomed transaction (deadlock
  victim, conversion error under `XACT_ABORT`) is open but uncommittable,
  and an `UPDATE` inside it raises a second error that hides the first.
- Ownership chaining: the `LOSS` login gets EXECUTE on the procedure and
  full rights on `stage`, and no INSERT on `dbo.Data`, `RMSELT`, or
  `RMS_HistoricalRDS`. Chaining holds only when the procedure and the target
  tables share an owner, so `loss_schema.sql` declares
  `CREATE SCHEMA stage AUTHORIZATION dbo` and must be run by a `db_owner`
  login (O-12). The body uses no dynamic SQL, which chaining does not cover.

**Alternatives considered**:

- *Worker-side set-based SQL through `db.execute_command`* (user 2026-09-03)
  — the client team could not run it; the transaction would belong to the
  driver. Rejected 2026-09-07.
- *Reserve a `DataID` before load* (note 23 D6) — the repository has no
  `SEQUENCE`, and a reserved ID does not stop a second load. Rejected.
- *Autocommit by `SET IMPLICIT_TRANSACTIONS OFF` inside the call* — pyodbc
  still opens a transaction per connection unless autocommit is set on the
  connection; the SQLAlchemy execution option is the supported way and the
  one `bootstrap_db.py` already uses. Rejected.

## R4 — Historical classification is a join to CIC's lookup with a one-match assertion first (T-04)

**Decision**: An event is `historical` when
`dbo.Lookup_RMS_HistoricalRDS` in the repository has a row matching
`EventID` and `ModelVersion = manifest.data_model_version`; otherwise
`stochastic`. Peril is not part of the join. The procedure fails when the lookup has no rows for the model version, and
fails when any stage `event_id` matches more than one lookup row, before the
classification `UPDATE` runs. The procedure names the lookup by its two-part
name `dbo.Lookup_RMS_HistoricalRDS` (R15).

**Rationale**:

- Note 23 D23 (classification by absence, confirmed by Cheng): the lookup
  holds historical events only. Note 23 D19: a model version missing from
  the lookup must fail the load, or every event loads as stochastic (spec
  non-negotiable 3).
- `UPDATE ... FROM` with a join that matches several rows does not raise in
  SQL Server; it picks one. The step-5 join for historical columns would
  then insert two `RMS_HistoricalRDS` rows for one loss. The assertion has
  to run first.
- The lookup DDL (`cic-reference/Lookup_RMSHistoricalRDS_v25DDL.sql`) is a
  heap with every column nullable and no index; `EventID` alone is not a
  key (it repeats across model versions, and possibly perils within one).
- The Risk Modeler ELT carries no peril per row (Parquet schema in R6), so a
  multi-peril group cannot be joined on peril; the assertion is its only
  protection (user 2026-09-04).

**Alternatives considered**:

- *Moody's event reference API* (note 24 D16) — APIs out; CIC's table is the
  source. Rejected.
- *A peril term in the join (`Peril = manifest.peril_code` for single-peril
  analyses, skipped for `YY` groups), held behind a procedure flag
  `@use_peril` defaulting to off until O-11 confirmed the lookup's peril
  codes* — dropped 2026-09-10 (user). Moody's `EVENT.csv.gz` reference
  export (6,099,671 rows, 5,729,443 distinct `EVENTID` + `MODELVERSIONCODE`
  keys, 2,754 of them `HIST`) has no key under more than one `PERILCODE`, so
  the term never discriminates against Risk Modeler's numbering. A duplicate
  typed into CIC's lookup is caught by the one-match assertion. Turning the
  term on before O-11 was the dangerous choice: a lookup holding display
  names such as `Windstorm` would match nothing and load every event as
  stochastic while the model-version assertion still passed. Dropping it
  removes the flag, the `YY` special case, and the former T-16.
- *Fetch the group's member perils from `get_regions` and join
  `Peril IN (...)`* — moot once the join has no peril term. Rejected.
- *Env var `MSSQL_LOSS_LOOKUP_DATABASE`* — a stored procedure cannot read an
  env var, and the var never existed in code. Rejected.
- *A synonym `stage.Lookup_RMS_HistoricalRDS` pointing at
  `CRE_Cat_Workflow.dbo.Lookup_RMS_HistoricalRDS`* (the 2026-09-09 morning
  decision, from the received DDL's `USE [CRE_Cat_Workflow]` header) —
  the user confirmed the same day that the lookup lives in the repository
  database; see R15. Rejected.

**Open evidence (O-04, O-11)**: whether `MAX(LEN(Peril))` and
`MAX(LEN([PCS#]))` in the live lookup fit the targets' `varchar(5)`, and
whether any `EventID` repeats within one `ModelVersion`. Until the CIC server
check runs, `PCS`/`Peril` are copied without truncation so an overflow fails
the load rather than storing a cut value (T-20), and a repeated event ID
fails the load through the one-match assertion.

## R5 — Two corrections, both automatic, both counted (spec P-03, P-04)

**Decision**: Where `loss > exp_value`, set `exp_value = loss` and flag the
row; where `std_dev_i < 0` or `std_dev_c < 0` on a stochastic row, set the
negative value to 0 and flag the row. Loss is never altered. Counts land on
the manifest and the export detail page.

**Rationale**: Note 24 D12–D15. Cheryl's condition for automatic correction
was "I would want to know that it's happening"; Wendy's was that the summary
carry row counts (note 24 D13). `RMS_HistoricalRDS` has no standard
deviation column, so the correction is stochastic-only (D15).

**Alternatives considered**: *Reduce loss to exposure* (the earlier
direction) — reverses model output. Rejected (note 24 D12). *A review step
before load* — retired (note 24 D14; spec out of scope).

## R6 — Archive layout, metadata, and the Parquet schema (T-07, T-11, T-13, T-20)

**Evidence** from the two captured archives:

| | DLM example (job 25437617, analysis 41958) | HD example (job 25827751, analysis 42044) |
|---|---|---|
| Top folder | `{JobId}_{AnalysisName}_Losses/` | same |
| Loss table folder | `ELT/` | `PLT/` |
| `metadata.csv` | `ELT/metadata.csv` | `PLT/metadata.csv` |
| Files | `ELT/Portfolio/{GU,GR,RL}/…_ELT_Portfolio_{P}_0.parquet` (one per perspective) | `PLT/Portfolio/{GU,GR,RL,RP}/…_PLT_Portfolio_{P}_{0..4}.parquet` (five per perspective) |
| `Engine Type` | `DLM` | `HD` |
| `ModelVersion` | `25.0` | `HDv2.1` |
| `AnalysisCurrency` | `USD` | `JPY` |
| `Peril` / `Region` | `Earthquake` / `NAEQ` | `TY` / `JPWS` |
| `PerspCodes` | `GU,GR,RL,TY` | `GU,GR,RL,RP` |
| Extra columns | — | `SubPerils`, `SimulationSet`, `NumberOfSimulations`, `NumberOfSamples`, `Shuffled` |

ELT Parquet schema (pyarrow, DLM GR file, 15,689 rows): `PortInfoId int32`,
`PortInfoName string`, `PortInfoNum string`, `EventId int32`, `Rate double`,
`Loss double`, `StdDevI double`, `StdDevC double`, `ExpValue double`. No
peril, region, or event-type column.

**Decisions**:

- The stage worker reads `AnlsId`, `ModelVersion`, `AnalysisCurrency`, and
  `Engine Type` from `metadata.csv`. `peril_code` and `region_code` come
  from `irp_analysis.settings_metadata` at submit (`perilCode`,
  `regionCode`; `analysis_service._parse_settings` already reads both)
  because the CSV carries display names. `AnlsId` is checked against
  `manifest.irp_app_analysis_id` and `AnalysisCurrency` against
  `manifest.data_currency` (spec FR-008).
- `ModelVersion` comes from the archive, never from the payload's
  `engineVersion` (`RL25`), because `Data.DataModelVersion` takes the
  decimal form (note 23 D9–D18).
- Several Parquet files per perspective is confirmed by the HD example, so
  the file grain (`stage.rwb_loss_result_file`) exists from the first build.
- `loss_table_type` and `engine_type` are stored on the manifest now so the
  HD path adds `stage.rwb_loss_result_plt_data` and `usp_load_plt_result`
  without altering existing tables. The PLT table is designed in
  [data-model.md](data-model.md) and not built (O-08).
- The DLM example's `PerspCodes` lists `TY`, and the HD example's `Peril` is
  `TY`; the parser reads perspective codes from folder names only, never
  from `Peril` (O-09).
- The stage worker only stages the Parquet files under the perspective
  folder matching `manifest.perspective_code`. The request asks Risk Modeler
  for one perspective, so any other folder is unexpected and fails the
  analysis (FR-008).

## R7 — irp-integration export methods on the active wheel (T-23)

**Evidence**: the active source is the `irp-testpypi` group, pinned to
`irp-integration==0.7.2` (`pyproject.toml` `default-groups`; `uv pip show`).
On that wheel:

- `analysis.submit_analysis_export_job(analysis_id: int, loss_details, file_extension="PARQUET") -> Tuple[int, request_body]`
  (`irp_integration/analysis.py:1625`). It resolves the analysis with
  `search_analyses(filter="analysisId=…")`, falling back to
  `appAnalysisId=…`, and POSTs `/platform/export/v1/jobs` with
  `exportType RESULTS`, `resourceType analyses`, one `resourceUris` entry,
  `settings.fileExtension`, `settings.lossDetails`. One analysis per job.
- `export_job.get_export_job(job_id) -> dict` — single status check
  (`GET /platform/export/v1/jobs/{jobId}`). Terminal statuses are
  `FINISHED`, `FAILED`, `CANCELLED` (`constants.WORKFLOW_COMPLETED_STATUSES`).
- `export_job.download_export_results(job_id, output_dir) -> path`
  (`export_job.py:126`): requires `FINISHED`, reads `downloadUrl` from the
  `DOWNLOAD_RESULTS` task, streams to a `.export-*.part` temp file in
  `output_dir`, rejects `text/html` and JSON content types, checks
  `Content-Length`, checks `zipfile.is_zipfile`, then renames to the
  filename in the URL. It calls `os.makedirs(output_dir, exist_ok=True)`.
- `poll_export_job_to_completion` exists and is forbidden here (Article 11).
- `app/services/irp_gateway.py` wraps none of the three; the `IRPGateway`
  Protocol, `_RealGateway`, and `tests/unit/fakes/fake_irp.py` each gain
  them.

**Decisions**:

- The submit worker passes `irp_analysis.irp_id` (the API analysis ID) as
  `analysis_id`; the `appAnalysisId` fallback is not relied on.
- The Workbench requires 0.7.2 or later. The one earlier live download
  (2026-02-16, notebook `export_flows.ipynb`, an older wheel) saved the
  Moody's Admin Center HTML page as the zip with HTTP 200; the content-type
  and `is_zipfile` checks now in the wheel are the fix. The stage worker
  treats an `IRPAPIError` from the download as a failed analysis.
- The stage worker checks that `EXPORT_ARCHIVE_DIR` exists **before**
  calling the download, because the library creates `output_dir` itself and
  would otherwise write the archive to local disk under an unmounted share
  path.

**Open evidence**: no export job has been submitted and downloaded end to
end by this codebase. The IRP sandbox test in [quickstart.md](quickstart.md)
is the spike; it is opt-in and needs credentials in `linux-box`. T-23 stays
Assumed until it passes.

## R8 — Loss repository DDL lives in two files; `bootstrap-loss` is new (T-22)

**Evidence**: `docs/DATA_MODEL.md` §1 names `db/bootstrap/loss_schema.sql`
and a `bootstrap-loss` command; neither exists (`db/` has no `bootstrap/`
directory; the Makefile has `db-bootstrap`, which runs
`infra/scripts/bootstrap_db.py` to `CREATE DATABASE` `rwb_workbench`,
`rwb_exposure`, `rwb_loss` and nothing more). The working design §3 says the
file "has no `stage` schema"; it has nothing, because it is not there. Note
23 O23-4 recorded it as "not yet present". Note 20 D19/O20-11: the loss
repository is a CIC-owned production schema; anything the repo holds for it
is a dev mirror that must never target production.

**Decision**: two files, one target.

- `db/bootstrap/loss_schema.sql` — what the CIC DBA installs unchanged
  (O-12): `CREATE SCHEMA stage AUTHORIZATION dbo`, the three stage tables
  with their `CHECK` constraints and indexes, and
  `stage.usp_load_elt_result`. Idempotent (`IF OBJECT_ID(...) IS NULL`,
  `CREATE OR ALTER PROCEDURE`). Names no database.
- `db/bootstrap/loss_dev_mirror.sql` — development only: `dbo.Client`,
  `dbo.Data`, `dbo.RMSELT`, `dbo.RMS_HistoricalRDS`, and
  `dbo.Lookup_RMS_HistoricalRDS` copied from `cic-reference/`. Seed rows
  come from `bootstrap_loss.py`: made-up clients and the historical
  subset of Moody's `EVENT` export (R16).
- A new `infra/scripts/bootstrap_loss.py` applies the mirror file, then
  `loss_schema.sql`, through `db.scripts.execute_script_file` on the `LOSS`
  connection (the trusted-script path handles `GO` batches; the target is an
  external schema, not the app's tables, so Article 7(b) permits it). Make
  target `bootstrap-loss` runs it inside `linux-box`; `db-rebuild` calls it
  after the migration.

**Alternatives considered**:

- *One file with the CIC tables inside* — the DBA would have to edit the
  file before installing, and a mistaken run would try to create `dbo.Data`
  on the production server. Rejected.
- *Alembic for the loss repository* — the repository is not the app's
  database, and Alembic's version table would land in CIC's schema.
  Rejected (DATA_MODEL §1 already excludes `LOSS` from Alembic).

## R9 — `CHECK` constraints instead of kind tables on the stage schema (T-19)

**Decision**: `stage_status`, `load_status`, `loss_table_type`,
`engine_type`, and `event_type` carry `CHECK (col IN (...))` constraints in
`loss_schema.sql`, not `*_kind` tables. This is a deliberate deviation from
Article 3, listed in the plan's Constitution Check and Complexity Tracking.

**Rationale**: the tables live in the client's repository and are written by
three workers and one procedure; a kind table there is five more tables the
CIC DBA seeds on every install and the procedure joins on every load. The
Workbench renders the values through Jinja labels, so no seed is needed for
display. User decision 2026-09-09.

**Alternatives considered**: *kind tables in `stage`* — rejected as above.
*Kind tables in `rwb_workbench` with the codes duplicated* — the FK could not
cross servers, so the constraint would be advisory. Rejected.

## R10 — Page reads of the manifest use a dialect-aware `READUNCOMMITTED` hint because RCSI is off (T-25)

**Decision**: every request-path read of `stage.rwb_loss_result_manifest`
(duplicate check, exports table, export detail page) appends the table hint
returned by a new `db.read_uncommitted_hint(connection)`: `WITH
(READUNCOMMITTED)` on SQL Server, empty on SQLite. The helper follows
`db.row_limit` (`db/execute.py:81`), which already branches on dialect.

**Rationale**: the load procedure holds an exclusive lock on the manifest
row from the claim to the commit, which can be minutes for a large analysis.
Under plain `READ COMMITTED`, the SQL Server default for an on-premises
database, the export detail page would wait for the commit. A dirty read of
one status row costs nothing; the unique index, not the read, is what stops a
duplicate. A raw hint in the SQL would break every unit test, which runs the
same queries over SQLite (R14).

**Evidence (2026-09-09)**: the user ran the `sys.databases` query on the CIC
server: `is_read_committed_snapshot_on = 0`,
`snapshot_isolation_state_desc = 'OFF'` for the repository. Plain reads would
wait on the load's row lock, so the hint is required, not precautionary.

## R11 — Export form and export detail are pages; the exports table is a section (T-26)

**Decision**: the export form is a page at
`/submissions/{submission_id}/exports/new`, reached from an **Export** button
in the analyses section's summary bar beside Compare and View; the exports
table is a section on the submission page below the analyses; the export
detail page is `/submissions/{submission_id}/exports/{export_id}`. Each page
is one hidden nav node under `submissions`, one handler, one template
(Article 1). Ticking analyses re-renders the perspective select, the
per-analysis data-name fields, and the exported marks over HTMX. Retry is an
`hx-post` on the detail page that re-renders the analysis row.

**Rationale**:

- The form has one text field per selected analysis and a duplicate check
  that depends on both the selection and the perspective; a page gives it
  room and a URL the analyst can return to (Article 8). The analyses section
  self-polls every 3 seconds while anything is live and would remove a modal
  mounted inside it; spec 013 needed an outside mount for that reason.
- User decision 2026-09-09 (spec O-06): exports live in their own table on
  the submission page; the analyses grid shows no export state.
- Both new screens have real new layout, so `docs/UI_WORKFLOW.md` asks for a
  rendered preview from `docs/ui_previews/_scaffold.html` before the
  templates are built. The tasks phase schedules that preview first.

**Alternatives considered**: *Export modal mounted outside the polling
section* (compare-modal precedent) — the per-analysis fields and the
selection-dependent re-render make the modal long and stateful; a page is
the boring option. Rejected. *Export status in the analyses grid* — rejected
by the user 2026-09-09 (spec O-06).

## R12 — Retry resumes from the manifest; the decision tree is the route's (T-28)

**Decision**: the Retry route reads the manifest row and the analysis's
`export` `irp_job`, then re-arms exactly one job through
`rwb_job_service.ensure_pending_rwb_job` and dispatches it:

1. `stage_status = staged` and `load_status <> loaded` → the
   `load_results_export` job.
2. Else, the archive is on the share (`zip_file` set and the file exists) or
   the `export` job is `FINISHED` with `completed_at` less than seven days
   ago → the `stage_results_export` job.
3. Else → clear `irp_export_job_id`, set `stage_status = pending` and
   `error_message = NULL`, and re-arm the `submit_results_export` job, which
   submits only manifest rows without a job ID.

A `loaded` analysis offers no Retry (spec FR-019, FR-021).

**Rationale**: the design §4.7 failure table; the seven-day window is the
export job's download URL expiry. `ensure_pending_rwb_job`
(`app/services/rwb_job_service.py:104`) resets a `succeeded`/`failed` row to
`pending` with `attempt_count + 1` rather than inserting a second one, and
the queue's `UNIQUE (requestor_type, requestor_id, rwb_job_type)` makes every
enqueue idempotent, so a re-fired poller tick or a double click cannot create
a second stage or load job. `portfolio_jobs._complete_breakout` is the
precedent for `ensure_pending_rwb_job` followed by `dispatch.dispatch`.

**Alternatives considered**: *Retry always restarts from submit* — costs a
new Risk Modeler export and a re-download for a load-only failure, and the
spec forbids re-downloading an archive already held (SC-005). Rejected.
*Automatic actor retries* — a failed load waits for a person or the
reconciler; an actor retry loop would hammer a deterministic failure
(lookup not loaded). Rejected; actors keep `max_retries=0`.

## R13 — Which analyses a submission can export, and where `Data.Name` and `Data.Description` come from (T-24)

**Evidence**: `irp_analysis` has no `submission_id` column and no
`description` column (`alembic/versions/0001_initial.py:469-535`); the
working design named both. Group analyses are `irp_analysis` rows with
`is_group = 1` and an `edm_id`, so they reach a submission the same way own
analyses do: `submission_edm`. Broker analyses reach it through
`submission_rdm`. `analysis_service.list_comparable_analyses(submission_id=…)`
already composes exactly that scope (own and group rows through
`_SUBMISSION_EXECUTED_SELECT`, then broker rows per RDM) and carries `id`,
name, origin, and results state. The Workbench holds two names per
analysis: `name` (≤256, the value Risk Modeler holds, truncated to 64 at
submit) and `full_name` (≤512, the untruncated portfolio + template name;
null on broker rows).

**Decisions**:

- The export form lists `list_comparable_analyses(submission_id=…)` rows
  whose results state is ready (`loss_results` present), extended with

  `irp_analysis.full_name` (null when absent). Note 23 D9–D18 recorded

  without naming columns; the Workbench's two names are the only candidates.
  This is Assumed until the user sees it on the export detail preview.

**Alternatives considered**: *`Data.Description` from

## R14 — Test tiers: SQLite for everything but the procedure; the procedure on SQL Server (T-27)

**Evidence**: `tests/conftest.py` registers a SQLite engine for `WORKBENCH`
only (`register_engine("WORKBENCH", engine)` at three fixtures); no `LOSS`
engine is injected anywhere; `tests/sqlserver/` has no conftest and no
loss-database provisioning; `tests/sqlserver/test_elt.py` exercises
`upload_parquet` against `WORKBENCH`. `db/scripts.execute_script_file`
splits `GO` batches. SQLite supports `ATTACH DATABASE ':memory:' AS stage`,
after which `stage.table` resolves, so the `stage.` schema prefix the app
SQL uses on SQL Server works unchanged over SQLite.

**Decision**:

- Unit tier: a `loss_db` fixture registers a second SQLite engine as
  `LOSS`, attaches an in-memory database named `stage`, and creates the
  manifest, file, and ELT data tables plus `dbo`-less mirrors of `Client`,
  `Data`, `RMSELT`, and `RMS_HistoricalRDS` from a SQLite mirror module next
  to `tests/iteration1_mirror.py`. Routes, the submit worker, the stage
  worker (with a fixture archive built from the DLM example's layout and a
  small Parquet file), the poller handler, and the Retry route run over it
  with `fake_irp`. `db.execute_procedure` is patched in the load worker's
  tests; the worker's entry checks and failure stamp are tested, the
  procedure body is not.
- SQL Server tier: a new `tests/sqlserver/test_loss_export_procedure.py`
  applies `loss_dev_mirror.sql` and `loss_schema.sql` to the `LOSS`
  connection at module start (idempotent), truncates the stage and mirror
  tables, seeds lookup rows, stages rows through `upload_parquet`, and
  calls `stage.usp_load_elt_result` through `db.execute_procedure`. It
  covers: lookup missing for the model version, one event matching two
  lookup rows, both corrections and their counts, historical
  column mapping and conversions, the claim raising on a second call, the
  `@@TRANCOUNT` guard, `CATCH` writing `failed`, and `loaded` set only on
  commit.
- IRP sandbox tier: one opt-in test submits an export for a finished
  sandbox analysis, polls `get_export_job` with bounded sleeps, downloads
  through `download_export_results`, and asserts the archive layout of R6.
  This is the T-23 spike.

**Alternatives considered**: *Mocking the stored procedure in SQLite with
Python* — would test a re-implementation, not the procedure. Rejected.
*Running the procedure tests against the shared dev `rwb_loss`* — the tier
truncates tables, so it needs its own schema; the mirror scripts are
idempotent and cheap, and `rwb_loss` holds nothing else. Accepted with the
truncation named in the test module docstring.

## R15 — One SQL Server, two databases; the lookup is in the repository (T-21, T-29)

**Evidence**: the user stated on 2026-09-09 that CIC runs one SQL Server
holding two databases: `CRE_Trial_ELT_Repository` and a Workbench
application database CIC has not yet named. `dbo.Client`, `dbo.Data`,
`dbo.RMSELT`, `dbo.RMS_HistoricalRDS`, and `dbo.Lookup_RMS_HistoricalRDS`
all belong in `CRE_Trial_ELT_Repository`. The server the user reached that
day (`CRE_Trial_ELT_Repository` at 5 MB of data with no `dbo.Data`, plus
`_HQ_2025_STD_CinciRe_HiDef_DEV` and `ServerControl`; RCSI off) is that
server; the repository is empty because CIC's load of the five tables
failed, not because it is a separate unpopulated environment. The received
lookup DDL (`cic-reference/Lookup_RMSHistoricalRDS_v25DDL.sql`) opens with
`USE [CRE_Cat_Workflow]`; that header records where the table was scripted
from, and the file is kept as received.

**Decisions**:

- The procedure reads `dbo.Lookup_RMS_HistoricalRDS` by two-part name. The
  synonym, the `CRE_Cat_Workflow` entry in `bootstrap_db.py`, the SQL Server
  tier's skip when that database is absent, and the separate SELECT grant
  on the lookup are all removed. Ownership chaining now covers the lookup
  read the same way it covers the three target inserts (R3). T-21 closes.
- `WORKBENCH` and `LOSS` remain two named connections even though both
  point at one host at CIC (note 25 O25-6 asked for exactly this). Nothing
  in the Workbench joins or transacts across the two databases; R1's
  manifest placement already assumes none. The Workbench database name at
  CIC is O-05's to collect; it is only ever an `MSSQL_WORKBENCH_DATABASE`
  value.
- `rwb_exposure` (`EXPOSURE`) is not used by any feature today. It was
  reserved as the source system for EDM/RDM imports, which the Workbench does
  not integrate with yet (user, 2026-09-09), so it has no counterpart at CIC.

**Alternatives considered**: *Keep the synonym so the lookup could move
later* — a synonym to a table in the same database is one more object for
the DBA to install with no reader who needs it; if the lookup ever moves,
the procedure changes in one `FROM` clause. Rejected. *One database for the
Workbench and the repository* — the Workbench's Alembic-managed schema would
land in CIC's repository; DATA_MODEL §1 keeps `LOSS` outside Alembic.
Rejected.

## R16 — The dev lookup seed is the historical subset of Moody's EVENT reference export (T-30)

**Evidence** (profiled 2026-09-10): the user downloaded Moody's Risk Modeler
`EVENT` reference table as `EVENT.csv.gz` (gzip-compressed CSV, 116 MB,
kept beside the repo at `../EVENT.csv.gz`, not committed). Inside: one
`~`-delimited CSV, 6,099,671 rows, 23 columns (`PERILCODE`,
`MODELREGIONCODE`, `MODELVERSIONCODE`, `EVENTID`, `EVENTNAME`,
`EVENTDESCRIPTION`, `EVENTTYPECODE`, `RDS`, `ISACTIVE`, `EXTERNALID`, …).
It holds stochastic and historical events together:

- `EVENTTYPECODE` is the historical marker: `HIST` 2,749 rows + `hist` 5
  rows = 2,754 historical events; `EP` (4,887,280) and `STOC` (1,209,637)
  are stochastic.
- `RDS` is **not** the marker: it is `true` on 5,201,320 rows, including
  4.2 M stochastic `EQ`/`EP` events.
- Historical rows by peril: `WS` 2,707, `EQ` 31, `WT` 10; by model version:
  13 versions from `7.0` to `25.0` (`11.0` 1,457; `7.0` 905; `13.1` 211;
  `15.0` 135; `25.0` 2, both `WS`/`INWS`).
- No repeated (`EVENTID`, `MODELVERSIONCODE`) among historical rows, so the
  one-match assertion (T-04) holds on dev data.
- `EXTERNALID` is empty on every historical row; `EVENTNAME` carries a
  4-digit year on 2,595 of 2,754 rows (`NOTNAMED, 10/07/1896`,
  `TW 1999 Chi-Chi M7.6 Event`); 9 rows have `ISACTIVE = false`.
- `PERILCODE` holds Risk Modeler codes (`EQ`, `WS`, `WT`), the same values
  `settings_metadata.perilCode` carries. Evidence toward O-11 for the dev
  seed only; CIC's live `Peril` values are still unverified.

**Decision**:

- `infra/scripts/extract_historical_events.py <EVENT.csv.gz>` writes the
  rows with `UPPER(TRIM(EVENTTYPECODE)) = 'HIST'` to
  `db/bootstrap/seed/lookup_rms_historical_rds.csv` (2,754 rows, committed;
  the 116 MB source is not). Column mapping to `dbo.Lookup_RMS_HistoricalRDS`:
  `EventID` ← `EVENTID`; `Peril` ← `PERILCODE`; `Type` ← `'HIST'`;
  `Name` ← trimmed `EVENTNAME`; `ModelVersion` ← `MODELVERSIONCODE`;
  `CatYear` ← the 4-digit year in `EVENTNAME`, `NULL` when absent;
  `[PCS#]` ← `NULL` (no source column). Inactive rows are kept: the live
  lookup carries no active flag.
- `infra/scripts/bootstrap_loss.py` loads that CSV into
  `dbo.Lookup_RMS_HistoricalRDS` after `loss_dev_mirror.sql` creates the
  table, and seeds `dbo.Client` with a handful of made-up rows.
- The `CatYear` and `[PCS#]` mapping is Assumed: CIC fills the live lookup
  by hand and may hold different values; the seed only has to make the
  procedure classify, so nothing in the Workbench depends on those two
  columns beyond copying them.

**Alternatives considered**: *A few hand-typed lookup rows for `25.0`/`EQ`*
(the R8 plan) — the file shows `25.0` has only two historical events, both
`WS`, so a hand-typed seed would test a shape the data does not have.
Rejected by the user 2026-09-10. *Filter on `RDS = true`* — includes 5.2 M
stochastic rows. Rejected. *Load the whole file and filter in SQL* — 6.1 M
rows into every `db-rebuild` for 2,754 useful ones. Rejected.

## Clarifications

### Session 2026-09-09

- Q: An analysis's Risk Modeler loss table export downloads and stages zero loss rows for the chosen perspective. Fail at stage, load a header row with zero loss rows, or fail inside the load procedure? → A: Fail at stage with "no loss rows for perspective {code}"; nothing reaches `Data`, `RMSELT`, or `RMS_HistoricalRDS`; Retry re-runs the check (spec P-12). A header row with no loss rows would be indistinguishable in CIC's tools from a broken load.
- Q: Risk Modeler accepts an export request but never reports FINISHED or FAILED. No Workbench timeout, automatic failure after a fixed wait, or analyst-driven restart of a waiting analysis? → A: No Workbench timeout (spec P-13). The analysis stays "requested from Risk Modeler" until Risk Modeler reports a terminal status, matching how analysis jobs already wait; Retry is offered only after a failure. A stuck row is cleared under O-01. Rejected: a fixed-wait failure (no observed hang justifies the branch) and restart of a waiting analysis (abandons a live Risk Modeler job).
- Q (user-raised): Dev replicas of `dbo.Client` and `dbo.Lookup_RMS_HistoricalRDS` need data. Where does it come from? → A: `Client` is seeded with made-up rows. The lookup is seeded from Moody's `EVENT.csv.gz` (user-downloaded, `../EVENT.csv.gz`), which mixes stochastic and historical events; only the historical events (`EVENTTYPECODE = HIST`, 2,754 of 6,099,671 rows) are loaded (plan T-30, R16).
- Q (user-raised): Where does database setup sit in the work order? → A: First. The dev mirror with both seeds, the `stage` schema and procedure, `bootstrap_loss.py`, and the SQL Server tier test of the procedure come before any route, worker, or template (plan T-31).

### Session 2026-09-10

- Q: An analyst picks the wrong client or treaty inception and clicks Export. No cancel, cancel per analysis while nothing is loaded (releasing the P-09 block), or a confirmation summary page before the export is accepted? → A: No cancel and no confirmation step (spec P-14). Each analysis processes to loaded or failed; a wrong client or date is corrected by CIC under O-01, like any other reload. Rejected: cancel before load (adds a cancelled manifest status, a filtered duplicate index, and a race with the stage and load workers to cover one mistake that O-01 already covers) and a confirmation page (story 1 asks for no further input after Export).
- Q: Treaty inception and CRM ID are pre-filled from the submission and editable on the export form. Is an edit recorded on the export only, written back to the submission, or are the fields read-only? → A: Recorded on the export only (spec P-15). Rejected: write-back (a side effect on a record with its own edit page, and a submission with several CRM IDs has no single value to overwrite) and read-only fields (forces a detour through the submission edit page for a value that only the load uses).
- Q: A group or broker analysis is reachable from several submissions. Which submission's exports table lists its export: the one it was requested from, or every submission that reaches the analysis? → A: The submission it was requested from, recorded on the export (spec P-16). Other submissions see the analysis marked exported on their form with a link to the export (FR-004). The manifest therefore carries `requested_from_submission_id` (data-model.md §4.1, plan T-32, added 2026-09-10); `irp_job.requested_from_submission_id` alone cannot list exports whose Risk Modeler jobs were never created. Rejected: listing on every member submission (one export would appear as several, and its client, inception, and CRM ID belong to one submission).
