### 3.2 Model version reverses (D11) ⚑⚑

Cheryl had spotted the problem before the call, from a structure comparison, and sent a screenshot:

> *"I think there's a difference between the historical data table structure and then how the data is coming through from the file that Wendy appended. I think there's probably some conversion of fields that happened, just like with that PCS number, that isn't actually consistent with how our data structure is in SQL… model version, if you look, it's actually a **char field as opposed to numeric field**. Ben's fix was a revert: *"That's what I had originally. I can just switch it back. ## 7. Dates go CRM-grained (D20, D21, D22) ⚑⚑⚑

This is the session's structural change, and Ben found it by asking about cardinality rather than about dates.

> Ben: *"Is it correct to say that a submission with multiple CRM IDs has multiple inception dates and expiration dates? One for each CRM ID."*
> Cheryl: *"Yes, technically that is true. They might be the same… every submission would be associated with the contract that would have its own inception expiration date. Now, it might be the same across all the CRM IDs that go with one analysis, **or they might be different**."*
> Wendy: *"most commonly, they would all have the same inception date, but it certainly would be possible to have different inception dates. **It's the expiration date that's probably more commonly different.** Because we got the annual and multi-year."*

The concrete case Wendy gave earlier: *"you can have an annual treaty and a multi-year treaty in the same submission **using the same modeling data** for those two treaties, and one's a one-year term and one's a three-year term."* She then said she could not think of a live example and found one on her own desk within a minute.

**D20 — inception and expiration become CRM-ID-level attributes, surfaced at the submission level.** Ben: *"it's almost like given a submission, if it needs to be able to contain multiple CRM IDs… **then the inception date and expiration date pair also needs to be the same number as however many CRM IDs that we have on submission**."* And the design: *"inception and expiration date becomes like a CRM attribute as opposed to a submission level attribute. It'll be seen at the submission level, but what I'm envisioning is displaying for a given CRM ID its individual inception and expiration dates **relevant only to that CRM ID**."*

**D21 — with a "make them all the same" control.** Cheryl's condition, priced: *"I'm okay with that if there's a button that says make them all the same. Because if I have 4 and we're going to say **85% of the time they're all going to be the same**, it's kind of an annoyance to have to enter it a bunch of times."*

**D22 — one row per CRM ID when Workbench data is extracted for linking.** Cheryl: *"if there are five CRM IDs listed here, I think we probably would want to see five rows of data, one for each CRM ID, even though the other stuff is duplicative. It's okay. And that would provide us information that we could use to link back to our system of record."* Ben confirmed it live: *"I'm storing CRM IDs against a submission via a join table. I'm not storing just a list against a submission"*, and demonstrated a four-CRM-ID submission producing four rows.

### What this collides with

**The schema is on Ben's side for D22 and against him for D20.**

| Fact | Where | Effect of D20 |
|---|---|---|
| `submission_crm_id` is a join table, *"0..N CRM-ID tags at the submission level"* | `DATA_MODEL.md:95`, `:121-127`, `:165`; `0001_initial.py:184-197` | **D22 is free.** The index `ix_submission_crm_id_submission_id` already supports the join. |
| `crm_id` is *"plain, unvalidated text; manual, optional"* | `DATA_MODEL.md:123`; `0001_initial.py:189` (*"unvalidated (FR-018)"*) | **D20 turns a tag bag into an entity.** Dates on an unvalidated, optional, possibly-mistyped tag need the tag to be meaningful first. `PRD.md:467`: *"hand-entered, optional, editable, **may be absent or mistyped**, many per deal."* |
| `submission.inception_date` is **NOT NULL** | `0001_initial.py:141` | **A submission with no CRM ID still needs a date**, so the column cannot simply move. Either it stays as the default/fallback, or FR:52 and spec 002 FR-001 change. |
| `inception_date` is a **primary filter** and the **default sort** | `DATA_MODEL.md:111`, `:163`; `0001_initial.py:179-183` (`ix_submission_list_order` on `inception_date DESC, name`); `FUNCTIONAL_REQUIREMENTS.md:114`, `:115` | **Filtering and sorting a submission list by a date that now lives one-to-many below it is a different query and a different index.** |
| `treaty_year` *"defaults to the inception year"* | `DATA_MODEL.md:163` | **Which inception year, when there are three?** |
| Inception is required at creation | `FUNCTIONAL_REQUIREMENTS.md:52`; spec 002 **FR-001** | Unchanged only if the submission-level date survives as the default. |
| Expiration date does not exist at all | grep across `docs/`, `specs/`, `app/`, `alembic/` returns **only** `18` O18-9's recommendation | **New column, wherever it lands.** |

**The cheapest shape that satisfies both D20 and the existing model** is to keep `submission.inception_date` as the deal-level default and add `inception_date` / `expiration_date` **nullable** on `submission_crm_id`, falling back to the submission's when null — which makes D21's "make them all the same" the *absence* of per-CRM values rather than a bulk write, and leaves the index and both specs untouched. **That is a suggestion, not a decision; the point is that the choice has to be made before a migration, because the alternative touches spec 002 FR-001 and the list's primary index.** → **O30-8**.

**And note what D20 does to `29` D2.** `014` FR-002 makes **data vintage required on the export form with no default**. `29` O29-12 already recorded Cheryl and Wendy wanting data vintage *and* expiration date on the submission page. **If the dates move to the CRM grain and data vintage follows them onto the submission, the export form's "required, no default" becomes "required, defaulted from the submission's CRM ID" — which is a better form and a changed requirement.** → **O30-8**, and see `29` **O29-4**.
