## 1. Analysis-metadata view & currency-scheme vintages (D1, D2)

Re-demo and extension of the `16` §1 analysis-metadata view — the "selected, not owned" pattern from `07` §2.1 and `14` §1.4. Ben restarted the app to walk Wendy through the whole flow; the metadata screen was the first stop.

### 1.1 Read-only reference, link-outs, and the read/write matrix (D1)

- The screen lists **model profiles, output profiles, event rate schemes, currencies, currency schemes, and vintages**, materialized in the Workbench DB from Risk Modeler and reachable via **quick links** to the right creation spot (currencies open in the Risk Modeler **admin center**, not the Risk Modeler UI). Maps onto `DATA_MODEL.md` §10 (`irp_model_profile`, `irp_output_profile`, `irp_event_rate_scheme`, `irp_currency`) + the "Sync IRP Metadata" action.
- **Read/write matrix clarified this session:** model profiles and output profiles remain **administrable** (create, delete, duplicate) from the Workbench via link-out; **event rate schemes are the only object that is read-only across *both* Workbench and Risk Modeler.** (Currencies are read-only in the Workbench; administered in the admin center.)
- Ben was candid the page "doesn't add too much value" as a frequent destination — its role is visibility + link-outs. The shared Risk Modeler **test environment** data is "gobbledygook" (266 nonsense currencies) because many people use it; production volumes differ. Reinforces the `16` O16-7 need for better filtering, not re-decided here.
- **Access-rights open item:** CIC asked whether a non-admin user could *view* the currency/reference-data screens in Risk Modeler. Ben's assumption — reference data is broadly viewable, editing gated by user rights, and Risk Modeler redirects a no-access direct link to the launchpad — is **to be tested, not asserted**. → O17-12.

### 1.2 Vintages as versions nested inside a scheme (D2)

- A **vintage** = a **version of a currency scheme**. The screen shows them **nested inside each scheme** (base currency, update interval, and each vintage's name/code, created date, effective date) rather than on a separate tab — Ben consolidated "two pages into one view."
- CIC was initially confused: they expected two **separate schemes** ("Ben 1", "Ben 2"), not one scheme with two vintages underneath. Ben demoed adding a vintage ("Ben 2", effective end of month; edited in Risk Modeler by **uploading a template file**) and the **RMS default** scheme. Resolution: **Risk Modeler keeps versions within a scheme** — different from how RiskLink organizes it — so a profile/analysis selection points at a **scheme *and* a specific vintage/version** (CIC's analogy: an "Intact" scheme with a dated version per year, pick 2026 vs 2027).
- Risk Modeler lets two vintages **share a name** (uniqueness is the combination of all attributes / effective date), so correct naming is on the user.
- **Data-model gap (new, load-bearing):** §10 models `irp_currency` only — **no `irp_currency_scheme` and no vintage table**. Surfacing schemes + vintages (and the submit-time picker, §2.2) requires both a scheme reference-cache table and a scheme-vintage table (base currency, update interval, vintage code/name, created date, **effective date**), synced from Risk Modeler like the rest of §10. → **O17-1** (supersedes the "add a scheme table" half of `16` O16-2, and extends it with vintages).

## 2. Currency out of templates → submit-time, suite-level selection (D4, D5, D6, D7)

The session's central thread, ~40 minutes. Reverses the `16` assumption that currency (a scheme reference) is a stored template field.

### 2.1 The problem: global, multi-currency books

- A worldwide book needs different currencies per country/region. If currency were baked into a template, a client run in USD, local currency, and euro would need **triplicate templates** — CIC called it "ugly" / "messy." Baking scheme+vintage in also means a template goes **stale** the moment a newer scheme/vintage releases.

### 2.2 Decision: currency is a submit-time parameter, not template config (D4, D6, D7)

- **Currency (analysis currency + currency scheme + vintage) is removed from the template/suite definition entirely** and chosen **at execution time** — "whether you're executing an entire suite, an individual template, or a handful." Defaults are pre-filled and **overridable**: **USD** analysis currency, **latest RMS** scheme, most-recent **currently-effective** vintage (a future-dated vintage won't auto-select). CIC: "default, perfectly fine … but still you got to force someone to look at it."
- **Defaults via application environment variables (D6):** the default scheme/vintage lives in the app's **env vars** on the VM, changed by **ops (Ross)**; **no admin UI and no RBAC** around it for MVP. CIC: "I think that sounds fine."
- **Never hard-linked (D7):** because currency is never tied to a template, **templates never go out of date**, and **CIC — not the system — decides when the default "flips."** CIC: "I just don't want the system flipping the switch. I want to flip the switch … we know on this date we updated currencies."
- **Reconciliation (heavy):**
  - **Remove `analysis_template.currency_code` (§7).** Currency is no longer stored per template; it's a run-time submit parameter (still maps to `client.analysis.submit_portfolio_analysis_job()`, just supplied at submit, not read from the row).
  - **This reverses `16` O16-2's** "template references the currency *scheme*." The **scheme/vintage reference-cache tables are still needed** (§1.2 / O17-1) for the metadata view and the submit-time picker — but nothing on `analysis_template` points to them.
  - **Env-var defaults are configuration, not schema** — record in §10/§14 as an app-config concern (no `default_currency` table for MVP). → O17-3.

### 2.3 Suite-level, and mixed-currency via regional suites (D5)

- Currency is selected at the **suite level**, not per template. CIC: "I think at the suite level."
- A **genuinely mixed** book (different local currencies within one run) is handled by **splitting into regional suites** — Japan in yen, Europe in euros, US in USD — each run in a single currency, rather than one global suite. Accepted as an **80/20** tradeoff; Ben acknowledged the fully-mixed single-run case is one he "can't automatically resolve," effectively "thrown over the fence."
- **Per-country currency within one suite is out of scope** — that unusual case is configured directly in Risk Modeler.
- Ties to **region as a selection axis** (`14` O14-3, still "display metadata" on §7 `region_label`): suites are organized by region (some by country), so region + currency-at-suite-level should be reconciled together with O17-6. → folded into O17-2.

### 2.4 Currency update cadence (open)

- Unknown how often Moody's/RMS pushes currency-table updates (cloud vs on-prem), and CIC must decide its own refresh cadence (monthly/quarterly/yearly). Bears on how "latest scheme/vintage" defaults behave over time. → O17-13.

## 3. Suites, duplicate-not-Excel, SQL edits, name uniqueness (D8, D9, D10, D11)

Advances the 8/14 suite-administration thread (`14` O14-1) and **re-scopes** the 8/18 Excel design (`16` O16-4).

### 3.1 No suites-of-suites (D8)

- The model **stops at one grouping level**: a suite contains templates, and suites are **not** nested inside other suites. CIC: "I don't know that we need suites of suites … it actually makes it easier for updates if you don't do it." Rationale: avoids the confusion CIC has seen in **AIR**, and prevents editing an underlying suite from unintentionally changing everything above it.
- Template **overlap** across suites is allowed at the **region/country** level but not at a **global** level.
- **Reconciliation:** **validates the existing `DATA_MODEL.md` §7 shape** — `template_suite` → `template_suite_item` → `analysis_template`, a single collection level. No schema change; confirms no self-referential suite nesting is needed.

### 3.2 Table Excel; build duplicate-and-edit instead (D9)

- Ben reported spending **~60% of a day** speccing an **Excel-based import/export** and hitting heavy complexity — **dependent dropdowns** (event rate scheme depends on model profile), model-profile metadata, and diff handling. Recommendation (accepted): **table Excel** (possibly revisit **~next month**), do **manual template/suite setup as a go-live/deployment activity**, and build a **duplicate-and-edit** feature now. CIC: "if it's very burdensome … let's just move over it."
- **Duplicate-and-edit flow:** copy a suite or template, **auto-append the name**, **swap the model profile**, **add/remove templates**, rename, save. Clearest use cases: copy a global suite and **remove the US** ("global ex-US"), or swap in an **updated model**. Ben: "The flow that I would envision is like duplicate." CIC: "Bingo. We're on the same page."
- **Reconciliation:** this **defers `16` O16-4** (the 8/18 two-sheet Excel **seed** + import/export with diff-apply). Consequence for §13: `analysis_template` / `template_suite` are **still not** in the kind-table seed checklist, and — with Excel tabled — the near-term seed path is **manual admin creation** (plus duplicate) rather than a seed workbook. The 8/18 dropdown/data-validation design (`16` D9) is parked with the Excel work. → O17-4.

### 3.3 Direct SQL edits for non-validated fields (D11)

- For fields that need **no validation** (chiefly **names**), editing the **SQL Server** database directly is an acceptable **bulk** path (e.g. mass renames), pending **write access from Randy**. Ben: "I don't see why not." Operational, not a schema change; note alongside `delivery_kind = sql` (§13) as an admin/ops affordance. → folded into O17-5.

### 3.4 Name uniqueness (D10)

- **Suite names and template names must be unique.** CIC: "suite names need to be unique, template names need to be unique." Driven by duplication pain in RiskLink today. Ben was checking his tables' constraints live.
- **Reconciliation:** add **UNIQUE** constraints on `template_suite.name` and `analysis_template.name` (§7) — an explicit **contrast** with `submission.name`, which §4 deliberately keeps **non-unique** (soft warning). Closer in spirit to the **blocking** EDM/RDM name-collision check. → **O17-5**.
