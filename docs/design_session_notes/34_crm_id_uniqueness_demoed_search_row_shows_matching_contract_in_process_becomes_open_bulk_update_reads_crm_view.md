## 2. CRM-ID uniqueness, built and demoed (D1, D2)

**The demo.** Ben on seeded data: *"I can't duplicate a contract, which is just the simple ask. **This contract already exists on this submission.** If I try to go add this contract to a completely different submission, I'll see the same thing. So it lets me get that far to be able to fill out these fields. And then stops me. It says this contract is already on this submission and **we can actually click the submission and open it into a new tab.**"* That's 9/22 D14 as Wendy described it (*"I'd go looking for that submission"*), with the looking done for her.

**What is built** (`27c702d`; `017` R14):

- **`uq_contract_crm_id`** (`0001_initial.py:211`): a plain unique index on `contract.crm_id`, case-insensitive through the database collation. The SQLite mirror uses `COLLATE NOCASE`.
- **One lookup per saved form**: `_prepare_contracts` runs `SELECT … FROM v_contract WHERE LOWER(TRIM(crm_id)) IN (…)` and raises `ContractInvalid` carrying the owner's id and name. The row being edited is excluded so a contract keeps its own CRM ID.
- **The race is handled**: `create_submission`, `add_contract` and `update_contract` catch the unique violation, re-run the lookup and raise the same error, so a concurrent save shows the owner rather than a 500.
- **Whatever the owner's status**: `017` FR-003 now reads *"whatever either submission's status."* A Completed or Cancelled submission still holds its CRM ID. R14 rejects a filtered index for that reason, and because the owner's status lives on `submission`, where an index on `contract` can't see it.

**D2, the consequence Ben showed next.** *"if I look for a CRM ID, it'll never show me more than one submission… **which is something that we wanted.**"* 9/22 D17's argument, that a CRM-ID search needs no contract rows because it returns one record, is now true by construction rather than by convention.

**One edge checked and closed.** The index is on the raw column while the service, the filter and the bulk script normalise with `LOWER(TRIM(…))`. SQL Server `=` ignores trailing spaces but not leading ones. **It doesn't matter here: `_prepare_contracts` strips the CRM ID before it is written (`submission_service.py:378`, `crm_id = (row.crm_id or "").strip()`)**, so the stored value and the normalised value agree. One line in R14 saying so would save the next reader the check.
