It was not mentioned today. Working from Risk Modeler's documented approach *may* have removed the derivation; it is not established that it did. **O22-1(b) stays open** (**O24-1**).

### 2.2 The rule, and the scope it applies at (D1, D4)

A conflict exists where two members share a **region / peril / engine-version** triplet but were run with different event rate schemes. That is the whole of it, and it has three consequences the group agreed on:

- **Same scheme → no prompt.** *"If you had two NAWS RL 23s, both stochastic, you wouldn't be able to choose this dropdown. It would be grayed out. Because there's only one event rate scheme."*
- **Different perils → no prompt.** Wendy's earthquake-plus-hurricane case: Cheryl, *"it will show you the rates for each peril grouping, and then you just go on… it's grayed out like what Ben's showing here, and then you just say next… There's nothing to do."*
- **Different engine versions → prompt, always.** Cheryl's reasoning is the domain fact behind it: *"you couldn't have picked something more recent than 23 if you ran it in 23 … it will force you, actually, it's not just the option, but either you stick with their default or you change it, but **you have to make a choice about what you want the model to use for the rate scheme**."*

Cheryl also named the workaround the design forces, which belongs in the UI copy: a scheme cannot be changed at grouping time on an individual member — *"you have to change it on the individual analysis first and then do the group."*

**One scenario is untested.** Cheryl raised the inverse pairing — a version 25 analysis run with the 23-equivalent latest rates, which would *not* conflict despite the version difference. Ben: *"I don't have that scenario, but I can make it."* → **O24-1**.

### 2.3 No default, on purpose (D2, D3)

Risk Modeler pre-populates; Workbench does not. The reasoning is recorded in two parts, and the second is more important than the first.

The mechanical reason: *"Have not been able to infer… how Risk Modeler chooses the default … There's not clear logic on how that's populated,"* and if the user simply presses next, *"the event rate schemes would be flattened to a single event rate scheme, this auto chosen one, which I cannot pick the right one every time."*

The client reason, which makes the divergence a requirement rather than a limitation: Cheryl, *"I don't know what the default, like how they're picking one versus the other either. And I'm not sure it matters. **We would not want to go with their default necessarily anyways.**"* Wendy pushed at the logic from four angles before letting it go — *"I was trying to like figure out what their default thought process is… if they're just going to like the lowest common denominator"* — and closed it herself: *"maybe we can't trust it anyway. I don't know. Just plow out with however we want to do it."*

**`22` O22-1(a) asked whether Risk Modeler's default (historical, in the 8/28 pair) is a rule or a coincidence. That question is now moot for the build** and survives only as curiosity (**O24-2**). What replaces it is a UI obligation: with no default, the selector is a required field, and the screen must say why.

The option list is narrowed to the schemes present among the conflicting members — *"I've chosen to limit the options to the event rates that are conflicting … We had two analyses in this group. They were run with these two event rates. Those are the options that you can pick"* — against Risk Modeler's full catalogue, *"This one has way more."*

### 2.4 Reconciliation — **O24-1**, **O24-2**

`22` **O22-1** had three sub-problems. **(a) is closed** by D1–D3. **(b)** — the region-peril simulation set — is unmentioned and stays open. **(c)** — where a group's chosen run parameters are recorded — is **unchanged and now more pointed**, because the chosen scheme is user input that exists nowhere else. §6's `submitted_settings` is documented as *"the run's own record of how it was submitted… own analyses only,"* explicitly lists **event rate scheme**, and is *"never updated afterwards"* — which is exactly the semantics a group's resolved scheme needs under Article 8. A group is an own analysis, not a broker row, so the null convention does not apply. Decide it there and **O22-3**'s mis-sourced group metadata gets the same answer, as `22` **O22-1(c)** already noted. Also confirm how the chosen scheme relates to §10's `irp_event_rate_scheme` cache and `workbench_is_active` (`18` **O18-1**) — the selector's option list is a *members-derived* set, not the cache's active set, and those two must not be confused in the query.

## 3. The grouping wizard, and what the screens owe the analyst (D5–D8)

### 3.1 Staged, not modal (D6)

### 3.2 Inspection is a gate (D7)

Already enforced: *"We cannot group. ### 3.4 Member-level context, including the non-conflicts (D8)

Wendy's scenario is the requirement: fifteen members, most irrelevant, conflicts possibly in several perils at once. *"Is the idea that am I only inspecting the conflict or am I inspecting all of them? … the reality is I could be grouping together 15 analyses."*

Ben's answer, and the spec text it implies: *"everything is inspected against each other. And every conflict should be displayed in a way that makes sense … these analyses have conflicting event rate schemes. This is the details that they were run with — region, peril, and engine version. And it should be clear that we have to choose an event rate scheme to resolve that conflict … And we can also say **these analyses don't conflict.**"*

He then demonstrated why the context is load-bearing by adding members live and surfacing a second conflict he did not expect, from a HU US group carrying 2023 rates.

Cheryl converted the requirement into a control: *"It'd also be nice to have a **carrot to expand it**. Her stated purpose: *"oh, I see, this analysis right here is the reason I'm seeing two different engine versions."*

**Risk Modeler cannot do this, and both clients noticed.** Wendy: *"there's just no information right here… about like which analyses are [involved]. How many or anything? Just kind of an interesting choice."* Cheryl: *"You can't drill down from here."* Wendy: *"I'd have to go back… and that's why I was like, well, if Ben can, in a good way, display that… make it easy for the user to see, oh, it's analysis 7 and 8 or whatever. **I think that's a win.**"* Recording that explicitly: this is a place where the design is deliberately **better** than the tool it mirrors, and it should not get value-engineered out later as a nice-to-have.

**Keep this distinct from `22` O22-3.** That item is the **member list on the group object** — Cheryl's coverage scenario, picking up a colleague's group and not knowing what is in it. This is the **builder and validation** surface. Different screens, different lifecycles; `22` **O22-4** already recorded the same care between the builder pick-list and `18` **O18-5**'s analyses grid. Both are needed and neither substitutes for the other. → **O24-3**.

### 3.5 Nested grouping — happening, and never designed

The most consequential unremarked moment of the session. Groups appeared as candidate members and as sources of conflict: *"which is probably for this group, HU US, that was run with a 2023 rate. So maybe **that group also has a conflict**,"* and, when checking a broker case, *"This is an analysis, not even a group."*

Three consequences nobody discussed:

1. A group member's event-rate conflicts are **transitive** — the parent's conflict set must include the child group's members' triplets. Today's third scheme option appeared for exactly this reason.
2. FR §6's *"Nested grouping (groups of groups) is supported"* has still **never been confirmed with CIC** (`22` **O22-2**), yet it is being exercised in the demo. The row is either a real requirement, in which case transitivity needs specifying, or an unvalidated assertion that just acquired accidental scope.
3. §6's `group_parent_id` self-reference already permits arbitrary depth. There is no stated limit and nobody asked for one.

→ **O24-4**.

## 4. Treaty conflicts — a warning, and a fact nobody records (D9)

### 4.1 The check, and why it cannot resolve

Risk Modeler's assumption is global treaty-number uniqueness — Ben: *"it assumes that treaty number is unique across the board,"* and against his own test data he does not accept it: *"Maybe this is just a result of my own messy test data, but I wouldn't assume that."* When members' applied treaties collide, *"there's no resolution at the time of grouping … The resolution is redo the analyses with either different treaty numbers or by fixing the treaties so that they have the same values."*

### 4.2 The agreed handling

Wendy's shape, accepted without argument: *"I think if you can capture the warning, even if you don't display any of this, I think is the right way to handle that. To just say, you have an inconsistent treaty warning, go resolve it or ignore it. **Because you do have the ability to ignore it in the system.** … you don't have to display it, you don't have to resolve it."* Two options only — Cheryl: *"Either ignore it and move forward or cancel and you have to go into Risk Modeler and fix it."*

Cheryl then made clear which branch is the common one, which matters for the default and the copy: *"Most of the time, it's not really fixable… you've got two independent treaty IDs… because they were run on different instances of this data, not pulling the same treaties, right? So it thinks that they're independent. They shouldn't be independent, but **99 times out of 100, I would say we accept the overlap** and just go ahead and move forward."*

Wendy asked for member identification in the warning — *"can you show in the error capture… what the analysis IDs or names are… instead of just saying somewhere, you have a [conflict], can you say like analyses, whatever, three, four, and five?"* Ben: *"I'd be able to build essentially the same table. We can take out some of the details, like if you don't want to see the treaty details, this red section."* Cost is not the issue: *"The validation, this validation is easy to implement."*

### 4.3 Reconciliation — **O24-5**, **O24-6**

Two things follow, and the second is a schema item.

**The requirement is a warning, not an error, and FR §6 has no row for it.** §6's one validation row is *"Invalid groupings show error messaging"* with the note *"e.g. mixing DLM and HD analyses."* `22` **O22-2** already asked for the event-rate case to be added there — **but today establishes that the event-rate case is not an error either.** It is a *required resolution*, and the treaty case is an *advisory warning with an ignore path*. Three distinct shapes, one row. §6 needs the row split rather than annotated.

**The warning needs applied treaties per member, and nothing records them.** §5 records `irp_treaty` per EDM and notes analyses reference treaties by name; §6 records nothing about what a run applied. `22` **D21** wanted them as a viewing column; `21` **O21-4** needs them to select for the TY export; the group warning needs them to validate. Three consumers, one missing fact, and `22` **O22-7** already proposed the landing spot — `submitted_settings` for own analyses, null on broker rows. **Note the awkward case that follows from that proposal:** the treaty conflict Cheryl describes arises between analyses run *on different instances of the data*, which in practice often means **broker rows**, where `submitted_settings` is null by design. If applied treaties live only there, the warning cannot fire for exactly the population that triggers it most. Resolve that before choosing the column.

## 8. Loss greater than exposure — corrected silently, reported afterwards (D12–D14)

### 8.1 The correction runs the other way

Ben opened with it backwards — asking whether the analyst edits the loss value to match exposure — and Cheryl corrected him immediately: *"Other way around. We'd set the exposure value equals the loss value. **We would not edit the losses coming out of the model.**"* That direction is the invariant: model output is never altered.

She was unsure who applies it today — *"trying to think if Cheng does that behind the scenes or if we have to; I think we have to manually go do it"* — and characterised the cause: *"there's a flag, but… it could potentially be thousands of rows that are off by, and usually it's the case where it's a rounding error, so you end up with, you know, pennies difference."*

### 8.2 Automatic, with one condition

Ben's proposal: *"Would it be appropriate to have that logic be built in automatically, to where if that scenario occurs, set the exposure value equal to the loss value. Always."*

Cheryl accepted with a caveat and a reason: *"I would want to know that it's happening, but at the same time, it's not going to be easy for us to update that information once it's on Risk Modeler anyways. But **I would want to know that it's happening.**"* Wendy closed it on the same logic — the loss repository is where the correction belongs because *"that's the place to go update it anyway."*

The reporting contract is Wendy's, and it is a requirement rather than a nicety: *"just the summary tells the user, you know, it's like you updated 10 rows or did you update 50,000 rows? **Because 50,000 rows is a problem. Like 10 rows is, who cares?**"* Cheryl's fallback if the number looks wrong: the data still sits in Risk Modeler, *"you'd still be able to look at the information to just do an eyeball check of, yeah, I'm okay with this, or know something's gone really terribly wrong."*

Ben's own framing of the summary: *"we can give you a summary afterwards saying that we found X number of rows that failed that validation and we applied that business logic to them."*

### 8.3 What this reverses (D14)

The design consequence is larger than the rule. Ben laid it out: showing the validation *before* loading means *"we have to already obtain all of the ELT data for every perspective, for every analysis that you could possibly want to export to the loss repository. So any imported analysis, any user executed analysis, we would have to get every ELT for every perspective loaded into the staging table… We just have to have all of the data on hand to do that validation on demand, **which would be storing a ton of data, most of which we probably would never need to load into the loss repository.**"*

With the correction moved after the commit: *"We don't have to orchestrate the procurement of those ELTs prior to actually being ready to submit."*

**This retires `22` D29.** The pre-fetch existed for one reason — so `21` **D18**'s integrity check could run on demand without a wait (*"I'm going to have this data ready regardless so that we don't have to do the waiting"*). Remove the pre-commit check and the justification goes with it. The trigger question of `22` **O22-10(a)** — which `20` **O20-15** answered *lazy*, `21` **O21-9** moved earlier and `22` moved earlier again — **settles back at lazy, on the export action**, and the storage-sizing worry at 100+ analyses × several perspectives under `{submission_outputs_dir}` (§9) dissolves rather than being answered.

### 8.4 Reconciliation — **O24-9**, **O24-10**

**`21` D18 is refined, not satisfied.** `21` §8.2 recorded loss>exposure as a must-have *review* step; it is now an automatic correction with a post-hoc report. `21` §8.4's *"corrections nobody sees"* category is exactly where it lands — and today's session adds a second member to that category (§9 below). Both need to be visible somewhere, which is a data question, not a UI one.

**Nothing in the schema holds the correction counts.** §9's `result_export` carries `delivery_code` and `location`; `analysis_result_meta` carries `elt_record_count`. There is no place for *"n rows had exposure raised to loss"* or *"m standard deviations were zeroed"* on a given export, and D13 makes those counts a client-visible requirement. Decide whether they are columns on `result_export`, a small child table, or part of a structured export report — and note `22` **O22-10(c)** already flagged that `result_export.location` is being asked to hold two things for one export, so the grain of that table is under pressure from two directions.

**While there, fix `elt_record_count`.** §9 documents its source as *"from get_elt() response"*, which `22` **O22-10(b)** established is wrong twice over — no count is returned, and the ELT no longer comes from `get_elt()`. With the pre-fetch gone the read happens at export time, so the natural source is a post-read count of the Parquet, taken on the same pass that applies the corrections. One fix, three items.

## 10. Event enrichment — reference data, not APIs, and not RiskLink (D16–D19)

The block that reverses `22` **D30** and settles `22` §11.4.

### 10.1 APIs are out (D16)

Stated as a standing position rather than a new conclusion: *"The enrichment of the events with their types. There's two ways that I can do that. One is with APIs, **which we are really leaning against.** The other is with reference data."* No dissent, no discussion.

**This reverses `22` D30's plan**, which was: get the Parquet, *"use the API to get every type for every event. Update the Parquet file itself with a new column."* `22` **O22-11(b)** had flagged the viability risk in that plan — *"I literally need to get the type for every single one"* — and it appears to have been decided against on those grounds rather than re-litigated. The sub-question of whether a bulk or filtered reference endpoint exists is **moot** if the data is loaded in bulk from a download.

### 10.2 Moody's answered, and Cheryl was right (D17)

`22` §11.4 recorded a genuine disagreement: Ben held that the reference tables *"have to exist somewhere"* in Moody's cloud because analyses use them, and suspected his Data Bridge SQL permissions; Cheryl held that they were RiskLink artifacts and that *"I don't actually believe that those reference tables exist on Data Bridge unless we have them build them,"* while allowing *"I could be completely wrong."*

The answer, from Moody's, reported by Ben: *"I do have a couple answers from Moody's team on this reference data. There's the event info table, which lives in RiskLink. **And you guys were right.** That does not live in Data Bridge. **That is not queryable via SQL for me.** That lives in two places: the API or manually downloadable from Risk Modeler, reference data, model events."*

Shape of what is downloadable: *"There is one big table for all DLM events, and then there's individual tables for… every HD analysis."*

**Consequences for the docs:** §1's `DATABRIDGE` connection is not a route to event reference data and never was — the constitution's Art. 11 read discipline is unaffected but the *expectation* recorded in `21` **O21-6** ("a source §1 has no connection for") is now confirmed as permanent rather than provisional. And `22` **O22-11(c)** is closed: not permissions, absence.

### 10.3 The coupling nobody wants, and the format everyone keeps (D17)

Ben's objection to the path of least resistance: *"I'm hesitant to be like, okay, it's easy to just use the RiskLink event info table because it has the data that we need, **because then that couples us to RiskLink now for reference data.**"*

Wendy's answer separates the product from the shape: *"I'm not really, I'm not attached to RiskLink, but **I might be attached to that data format in SQL**, if that makes sense, for DLM models,"* and on the durable dependency: *"I agree, there shouldn't be… a perpetuated link… five years from now to a RiskLink server, but it would be to that data table that's sitting on our current server."*

Ben's summary of the alignment, which is the decision as recorded: *"Querying the RiskLink event info table to do data enrichment for DLM models is not the right approach, but querying the equivalent data — whether it's downloaded from here or probably downloaded from here… obtaining DLM [reference data] from here, loading it into a SQL database that will serve as the reference event lookup reference for the Workbench enrichment process, is desirable. Maintaining that in SQL, but not using RiskLink event info table itself."*

Wendy added the qualifier that keeps the door open: she cannot guarantee the RiskLink-side dataset stays current forever, and Ben said the same — *"I don't know if we can guarantee that they'll keep this dataset in RiskLink up to date forever."*

### 10.4 The unmade decision, and why it is a governance question

Cheryl's objection, twice stated and never answered: *"theoretically, for DLM, if you created the same table using the data off Risk Modeler, **it should be the same as what we've already created.** So it's extra work on your part to come up with the same end results, I think. We might want to confirm that."*

Two options, materially different in the data model:

| | Read CIC's existing lookup | Build and hold our own |
|---|---|---|
| Connection | Foreign read over `LOSS` (Wendy, 9/1: the lookup sits on the loss repository server and she offered to move it) — same shape as the client table after `22` **D25** | A new dataset the app owns; either a **fifth named connection** or a table inside `WORKBENCH` |
| §10 invariant | Untouched — a read, like every other reference read | **A second carve-out** to *"the app never writes to the reference cache"*, alongside `18` **O18-1**'s `workbench_is_active` |
| Sync burden | None — one copy, CIC maintains it, Cheng's process already keeps it current | Two copies for as long as RiskLink 25 and Risk Modeler both run (§10.5) |
