## 6. The treaty key — `26` O26-5 answered (D8, D9)

This is the part of the call with consequences outside the export.

### 6.1 What `26` left open

`26` **O26-5** refused to settle the key: `24` **D9** recorded **treaty number**; on 9/3 Wendy read the behaviour as the **ID field** (*"I think that's what it's doing"*), Cheryl agreed twice in hedged terms, and **Ben, reading his own screen, said the opposite** and conceded only *"you're probably right."* `26`'s verdict: *"Three hedged agreements against one direct screen reading is not a finding… Verify against the API / the treaty payload, not by consensus."*

### 6.2 What today established

Ben asked whether treaty IDs are unique, and Wendy — the 9/3 advocate for the ID — supplied the mechanism that dissolves the disagreement:

> *"They're unique for the analysis… but it recognizes there's a different identifier that recognizes that it's the same treaty that you started with… **this 7655 is created at the time of the analysis. It's not the same treaty identifier.** This is one of the most confusing things about RiskLink… **this is not the original treaty identifier. It's the one that got generated with the analysis.**"*

And the validation path:

> *"The treaty validation that you're talking about, the inconsistent treaties, **happens on the loss side**… when you get an inconsistent treaty warning, it's because **it's not looking at that new identifier. It's working its way back** to what was stored in the RDM… It's not going back to the EDM to validate it. It's only looking at what's in the RDM… **because there's a fundamental principle that EDMs and RDMs are not linked**… because a group is an analysis. A group is a loss analysis."*

Cheryl then opened the table in SQL, on the same RDM Wendy had been demoing:

> *"There's a table in the RDM — so this is not the EDM, this is from the RDM, the results — called **treaty description**. And what you see is here's the treaty ID that you saw in the user interface. And **each one of those goes back to a specific treaty number and treaty name**… The treaty number and the treaty name, I think that's going to have to be consistent. So 7655 is going to link with 7658 is going to link with 7661 because **they all link back to the same treaty number and treaty name**. And this is the grouping."*

**Both 9/3 readings were half right.** There is a per-run identifier, and Wendy was right that it differs between runs of the same treaty; and the comparison resolves *through* it to the number and name, which is what Ben was reading off his screen. **The key is the treaty number (with the name), and it lives on the loss side, in the RDM.**

### 6.3 The caveat, and why it is not small (D9)

> Ben: *"The treaty number in Risk Modeler is unique **within a given EDM**."* Wendy: *"That's true."*
>
> Ben: *"And that's definitely **not unique across EDMs**, because I have multiple copies of the same treaty across duplicate EDMs that I've imported many times."*

`21` **O21-4(c)** already required the **EDM boundary enforced as a hard block** for TY export, by analogy with `20` **D17**'s currency guard. **Today supplies the failure mode that makes it mandatory: a cross-EDM TY aggregation keyed on treaty number would merge two unrelated treaties silently, producing a plausible loss set that is wrong.** Cheryl's 8/26 reasoning — *"they would be given different IDs because they came from two different sources"* — was about identity; this is about the number colliding rather than differing, which is the more dangerous direction.

### 6.4 Reconciliation — **O28-4**

**Against `spec 012`, written in the gap:** **FR-020** already specifies *"one table per mismatched **Treaty Number**"* with columns *"treaty id, **Treaty Number**, treaty type, effective and expiration date, attachment point, occurrence limit, per risk limit, currency"*, and **Non-negotiable behavior 6** reads *"Loss-affecting treaty terms sharing a **Treaty Number** are compared at inspection."* **The spec chose treaty number without the confirmation O26-5 demanded, and this session vindicates it.** Record the evidence so nobody reopens it; note that the spec also shows **treaty id** in the table, which is correct as a display fact and must not be mistaken for the key.

**Against the data model, where the problem remains:** §5 records `irp_treaty` per EDM and states *"Treaty is referenced by analyses **by name**"*; `submit_portfolio_analysis` passes `treaty_names: list[str]` (`irp_gateway.py:989–1008`). **So the attribute the Workbench submits is a name, the attribute the results expose is a per-run ID, and the attribute the comparison keys on is a number — three different things, and the model records none of them against an analysis.** `22` **O22-7** and `26` **O26-6** are the same gap; today tells them what to record. → **O28-4**, **O28-6**.

**And bank Wendy's structural statement.** *"EDMs and RDMs are not linked"* is the reason the applied-treaty fact cannot be resolved by walking back to the exposure side at read time. It has to be captured on the loss side, at or after the run — which points at `submitted_settings` for own analyses (with the usual broker hole, `24` **O24-6**) or at a retrieval-time snapshot alongside `analysis_result_meta`.

## 7. Naming, default rows and traceability (D13, D14)

The CIC workflow tool already solves the part the analyst touches, and Wendy demoed it.

- **One row per treaty, automatically.** *"You would pick the two… you'll get two separate rows. And then they get a default name put on them that says like PPR1, PPR2 — there's some logic that says the name of the treaty is this, so I'm going to put the name into the data table and then the analyst will give it a new name."*
- **The default name is informative, not filler.** Wendy called it *"kind of a default garbage name"* and corrected herself immediately: *"it's not really a garbage name. It's actually very informative. It actually tells me that this data ID was layer one, this data ID was layer two."* Cheryl explained the content and its source: treaty number plus **occurrence limit** and **attachment point**, read from the same `treaty description` table — *"we can identify roughly what treaty it goes with without having to go all the way back. - **The identifiers ride along for traceability.** *"The treaty ID is actually captured in another field in the table, so that I know what came through in which group. And it sort of gives you a way back to the data, because every result, you have to swim your way back to which treaty it was. So it actually gives you a little bit of a roadmap for that."*
- **Analysts rename afterwards** — *"I will typically go in and rename those so they're a little more informative"* — so the generated name is a starting point, not a contract.

**Requirement, not nicety.** Two per-risk layers of the same program differ only by attachment and limit; a data row named after the treaty alone is indistinguishable from its sibling. **Whatever the Workbench writes must encode enough of the terms to tell layers apart, and must carry the number, name and per-run ID as fields.**
