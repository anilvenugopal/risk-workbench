## 3. ELTs out of viewing scope, and the storage decision that followed (D5, D6)

The most consequential thread of the session. Recorded in full because it reverses a working assumption in §9 and in `05`.

### 3.1 The question and the answer

Ben, having built EP-curve and AAL displays: "my understanding was that the loss repository houses ELTs. Is there a requirement to view ELTs for [the] workbench?"

- **Cheryl: no.** "If somebody really wants to look at the event information underlying, I think you can go into Risk Modeler and get that. Because I think that is not a common scenario. I think it's less common."
- **Cheryl immediately fenced the exception:** "But we will need the ELT, right? I mean, to export — we don't need it for viewing." Wendy corrected her own phrasing to agree: "not for viewing."
- **Wendy on the positive requirement:** "We don't need to go back to the ELT for what we're trying to do. We just need the stats, the AAL and the EP curve, which should be a lot less data."
- Ben's reaction was about build cost, not politeness: "You've made my life really so much easier with that singular sentence. Building out this view has now become really much simpler from a technical perspective. These data sets are huge, and getting them from the APIs is sketchy when they're so massive … and there's not a great way to filter specific things that we want."

### 3.2 The three endpoints, and why the answer matters

Ben enumerated the API shape on the call, and it maps cleanly onto §8's `retrieve_analysis_results` (`get_elt/ep/stats/plt()` per perspective):

| Data | Endpoint | Needed for viewing? | Needed for export? |
|---|---|---|---|
| **AAL / stats** | EP stats (`get_stats()`) | **Yes** | Yes |
| **EP curve** | EP curve (`get_ep()`) | **Yes** | Yes |
| **ELT** | ELT (`get_elt()`) — "massive," paginated | **No** (D5) | **Yes** — loss repository |
| **PLT** (HD only) | `get_plt()` | **Not discussed** | Presumed yes |

Note Ben's own framing was "that's three different endpoints" for stats / EP curve / ELT, while his conclusion — "I can get all of this in a single API call" — refers to the **EP curve** specifically, in contrast to the ELT's pagination. **The viewing path is therefore ~2 calls per analysis per perspective, not one.** That distinction is load-bearing for **O19-2**.

### 3.3 Decision: don't store loss results for the view path (D6)

Ben talked the storage question through out loud and landed it on the call:

> "Do we store loss results in the Workbench … Do we store massive ELTs in tables on the Workbench database? Do we store Parquet files somewhere? … If we have the standard subset of EP curve points that we want to see for condensed display and expanded display, **I won't even store this data on the Workbench at all.** … We'll rely on API calls to pull this data, and that should be reliable and performant. As opposed to storing this information either in a tabular form or in a Parquet format and subsequently querying that."

He was explicit that this was PremiumIQ's question, not CIC's — "these are not questions that you need to answer, these are questions we're trying to answer" — but that CIC's requirement determined the answer.

### 3.4 Reconciliation — **O19-1**, **O19-2**

**§9 is not deleted; its purpose narrows.** The Parquet layout, `analysis_result_meta`, `result_export`, `delivery_kind`, and the `retrieve_analysis_results` / `download_export_file` / `push_results_to_loss_repo` job types remain **exactly right for export**, which is where the ELT retention D5 preserved actually lives. What changes is the **trigger and the read path**:

- **Read path (viewing):** live IRP calls, no SQL, no Parquet. Constitution Art. 5 puts polling/result work in workers — a **synchronous read on the request path** for a user-initiated view is a different animal from retrieval-and-materialization, but it should be stated deliberately rather than assumed, with a **timeout and failure story** (what the results page shows when Risk Modeler is slow or down — today's design has no fallback because it has no cache).
- **Trigger (materialization):** decide **eager** (fire `retrieve_analysis_results` on analysis completion, as the current model implies) vs **lazy** (fire it only when an export is requested). Lazy is the honest reading of D6 and avoids materializing 100+ analyses nobody exports; eager keeps export instant and — importantly — keeps `analysis_result_meta.aal` populated for the grid. **These are the same decision.** Do not settle it before **O19-12** (export requirements, 8/26) — but do not let the results view ship assuming the row exists, either.
- **`analysis_result_meta` fields that viewing no longer justifies:** `elt_record_count`, `elt_file_path`, `has_plt`, `plt_file_path` are now export-only. `ep_file_path` / `stats_file_path` likewise. **`aal` is the exception** — see below.
- **The `05`/FR "ELT summary is shown: AAL, max event loss, record count" requirement is now inconsistent with D5** — max event loss and record count come from the ELT endpoint. Either that row drops to export-only, or viewing calls `get_elt()` after all, which defeats D5. → folded into **O19-13**.

**O19-2 — the AAL column is the counter-pressure.** D10 puts **AAL as a column on the analyses grid**, and `05` §7 records analysis counts of **4 to 100+ per submission**. Live-fetching AAL per row per perspective turns a list render into a fan-out of dozens to hundreds of calls. Options, in preference order:

- **(a) Keep `analysis_result_meta.aal` populated eagerly** (a lightweight stats-only retrieval on completion, deferring ELT/EP materialization to export). Cheapest correct answer; preserves the grid, keeps `05` §7's volume guideline achievable, and leaves D6 intact for the *detail* view, which is what Cheryl and Wendy were actually talking about.
- **(b) Live-fetch AAL with a short-lived server-side cache** keyed on analysis + perspective. Preserves "store nothing" literally, at the cost of a cache nobody has specified.
- **(c) Live-fetch per row, uncached.** Not viable at 100 analyses.

Recommend **(a)**, and record it as a deliberate narrowing of D6 rather than a contradiction of it: **detail views are live; the one summary number shown at list scale is cached.** Confirm with Ben before building the grid column.
