## 3. The export architecture (D3, D4)

Anil's presentation was deliberately compressed — "I'm not going to drain all of the design details" — and rests on a single premise.

### 3.1 The premise

> "What we want to do is build a **resilient, recoverable** solution for exporting the data from Moody's for analysis results into the loss repository. And it means that data needs to take **multiple hops**. We want to manage those hops in such a way that **analysis becomes the unit of execution and the unit of recovery**."

This is a stronger statement than anything in `DATA_MODEL.md` §9, and it is the right unit: an export batch may name several analyses (D9 writes one `data` row per analysis), and a partial failure must be recoverable per analysis rather than per batch.

### 3.2 The mechanism

> "We want to move away from managing files, downloaded files, to **managing things on a database**. What does that mean? We download a file … it's a zip file, we want to unzip that file, we want to **make a manifest** of what is contained in that zip, and put the manifest and **upload all of the files that have been downloaded into a staging table**. … There is an **enrichment** that needs to happen. We want to do that enrichment **in the database rather than do that on files so that it's transaction managed**. And once the stage is ready, then we can say, **export this analysis to loss repository** on the screen. And we want to do a **move from that stage into the target**."

Four properties worth pinning, because they are design commitments and not implementation detail:

1. **The download is not the checkpoint.** "We download a file, we don't want to stop the download at that stage" — the zip is expanded and landed before anything is considered complete.
2. **The manifest is a first-class artifact**, written alongside the files. Note this word recurs on the *target* side too (D9 / §5): the CIC `data` table is itself "really just a manifest."
3. **Enrichment happens in SQL, for transactionality.** This is the justification for staging existing at all.
4. **Stage → target is a user-triggered move**, not an automatic consequence of retrieval. The screen action is "export this analysis to loss repository."

### 3.3 The code is ahead of the documentation

`db/elt.py` — Anil's own work, merged before this session (PR #91 `elt_utilities`; commit `b883116` "Add db/elt.py: Parquet bulk load and DataFrame enrichment") — already provides exactly these primitives:

> `upload_parquet: stream a Parquet file into a SQL Server table.`
> `enrich: set-based UPDATE of a SQL Server table from a pandas DataFrame, matched by a single or composite key, via a session-scoped temp table.`

So D3/D4 is a **design write-up of a proof of concept that exists**, which is good news for the schedule and bad news for the docs. `DATA_MODEL.md` §9 has `analysis_result_meta`, `result_export` and `delivery_kind` and **no staging concept whatsoever**; §12's table manifest has no row for one; §8's `push_results_to_loss_repo` is described as "Read Parquet; write to LOSS DB," which is now the *last* hop rather than the whole job. → **O23-2**.

Note also the `db/README.md` split: `db.execute` (bound parameters, all application data access) vs `db.scripts` (text substitution, trusted curated SQL, worker-side, DataFrames, "must never touch the app's own tables"). The staging/enrichment path is worker-side and DataFrame-shaped, so it sits naturally on the script path — but the staging tables **are** app-owned tables, in a database the app does not own. That tension needs a stated answer. → **O23-2**.

## 5. The reduced ask — reserving data IDs (D6)

The most constructive move of the session: rather than defend the full request, Anil mapped how much of the design survives without it.

## 8. Stochastic vs historical — `22` O22-11 substantially resolved (D23, D24) ⚑⚑
