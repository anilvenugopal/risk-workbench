## 0. TL;DR

The session where the rebuild stops being a claim and starts being evidence — and where three requirements land so cheaply that they are worth writing down before anything else, because each is a one-line change today and a migration later. It is also the session that opens a design surface nobody has documented: HD grouping does not resolve on event rate schemes at all, it resolves on simulation sets, and the repo has never heard of them.

## 3. The wizard as built, and the fast path (D2–D5, D8–D10)

### 3.1 Three screens, and what each carries

Small, unambiguous, and a real behavioural divergence from Risk Modeler in **both** directions.

Ben, demonstrating: Risk Modeler *"does not auto-populate a currency. I had to pick it. It was actually empty… being able to proceed was blocked until I picked a currency. I don't do that in the Workbench. I just default to USD."*

Neither behaviour is wanted. **Where the members' currency comes from matters.** §6 records that `submitted_settings` holds the approved plan item including *currency (code, scheme, vintage, `asOfDate`)*, written verbatim at claim time and never updated (Article 8), and that **currency scheme and vintage exist nowhere else** — chosen per suite at submit time (spec 009 P-11). ### 6.1 The requirement

Cheryl raised it in the last five minutes, after Wendy had left, prefaced as *"pretty minor"* — it is not.

> *"I'm going to take us back to the DLM version with multiple rates, and your choice to only select the rates that were in the analyses that are being grouped… **We will always want to have the RiskLink 25 rates available.** So if we could just make sure that always includes — and this is really an issue for windstorm only, right? ### 6.2 What it changes — **O26-7**

`24` **D3** made the option list **members-derived**, deliberately narrower than Risk Modeler's catalogue (*"This one has way more"*), and `24` **O24-1** closed with a specific warning:

> *"the selector's option list is a members-derived set, not the cache's active set, and those two must not be confused in the query."*

**D11 makes it both.** The list becomes a union: the schemes present among the conflicting members, **plus** a peril-scoped floor — for windstorm, CIC's default rate set. 1. **Is `workbench_is_active` the same set as "our default rate set"?** Nobody said so; it is an inference, and a wrong one silently changes what analysts can pick.
2. **Is the floor really windstorm-only?** Cheryl was explicit that earthquake *"is a different situation"* and did not say what that situation is. Do not generalise the rule to all perils, and do not hard-code the peril either — ask what earthquake needs.
3. **Does the floor apply only where a conflict already exists?** Cheryl assumed so — *"it would have to be a mismatch case where I could even pick it anyways, I get that"* — which means the floor widens an existing choice rather than creating one. That keeps `24` **D4**'s greyed-out behaviour intact for the no-conflict case, which is worth stating explicitly so it is not eroded.

Note the interaction with §6's `submitted_settings` (`24` **O24-1(c)**): if the user picks a scheme that **no member ran with**, the group's recorded scheme is neither derivable from its members nor present in any member's run facts. That is the strongest argument yet that the chosen scheme must be recorded on the group row rather than inferred.
