## 1. The flow, as presented

Recorded because this is the first time the whole export chain has been stated end to end to CIC, and because two of its steps have no `rwb_job_type`.

Ben's framing, which is also the standing justification for the entire export feature: "we have analyses that live on Moody's that **do not live in any database table that we can query** at the moment. So we'll be obtaining these loss results via downloading Parquet files. We'll need to process those, enrich those with metadata, and save them to the loss repository that's currently used today."

The chain:

1. **Obtain** the results archive from Risk Modeler (`22` **D28** — a job request naming the analysis, the ELT at portfolio output level, and the perspective codes).
2. **Download** the zip onto the application VM.
3. **Unzip**, and **build a file manifest** of what came back.
4. **Stage** the ELT data into a database table — "that's a major question for you, Nagi."
5. ~~*(dropped)*~~ — the pre-load validation display, removed by the morning session's loss>exposure decision.
6. **Enrich** the staged data with event metadata, by SQL join on event ID.
7. **Copy** into the loss repository: "**there's 3 tables we need to write to.** One is a data table, which is kind of like a manifest table almost. And then there's two separate tables for the actual event loss tables."

Steps 1–4 and 6 are "**a chained ETL sequence orchestrated by the Workbench**" — which is Article 10's queue and §8's chaining, and is exactly right in shape. It is the granularity that does not match: **§8 declares two job types for this whole chain** — `download_export_file` ("Download Parquet export") and `push_results_to_loss_repo` ("Read Parquet; write to LOSS DB") — and neither describes unzip, manifest, stage or enrich. `push_results_to_loss_repo`'s stated responsibility, "read Parquet; write to LOSS DB," is now **wrong in the middle**: the path is Parquet → staging table → SQL enrich → target tables, not Parquet → target. → **O25-5**.

**What did not come up, and should be noted as absent rather than settled:** which reference table the enrichment joins to. Ben's phrasing was "**probably** one that we'll confirm with Cheng this afternoon, but probably one that already exists that the workflow application uses today." That is an assumption carried into an approved design. It is `24` **O24-11**'s question — *decide whose table* — and it gets answered in the Cheng call at 1:00 pm Central, not here.

### 3.3 Reconciliation — **O25-1** (the manifest's home and grain) ⚑

`23` **O23-2** already framed this — "the staging tables … are app-owned tables in a database the app does not own, which is a **new category** not covered by §1's 'Managed by' column or §14," and its (e) asked whether the source-side manifest and CIC's target-side `data` table "are the same concept at two hops." **Today does not answer that; it removes the condition that was deferring it.** Approval means the DDL now has to be written, so the question stops being architectural hygiene and becomes the thing blocking a deliverable. What this session adds to O23-2 is a third overlap it did not name, and a cheap resolution.

**The manifest table Ben described and `analysis_result_meta` (§9) are largely the same table.** Compare:

| Ben's manifest (in `LOSS`) | §9 `analysis_result_meta` (in `WORKBENCH`) |
|---|---|
| statuses that drive the process | — (status lives on `rwb_job`, §8) |
| IDs to the appropriate Risk Modeler entities | `analysis_id` / `rdm_id`, `analysis_name` snapshot |
| attributes common across the ELT rows | `perspective_code`, `aal`, `has_plt`, `retrieved_at` |
| references back to the downloaded zip / result file | `elt_file_path`, `ep_file_path`, `plt_file_path`, `stats_file_path` |

§9's stated purpose is "SQL stores **only the metadata needed for export lineage**," and §9 puts it in the Workbench database. Today's decision puts a table with the same job in the loss repository database. **Both cannot be the record.** Three questions, in order:

1. **Is the manifest `analysis_result_meta` under another name, or a genuinely second thing?** A defensible split exists: `analysis_result_meta` is *retrieval* lineage (what was fetched, from where, when), and the manifest is *load* state (what is mid-flight into the repository, at what status, from which archive). If that is the split, say so in §9 and name them differently — "manifest" for both invites exactly this confusion.
2. **If it is load state, does it belong in `LOSS` at all?** It is state that **drives an application process**. Article 7 splits `/db` into a safe bound-parameter path for application data and a **trusted-script path for "curated, team-authored scripts against external sources only,"** which "MUST NOT target the app's own tables." A driver table in an external database is the awkward case that clause did not anticipate: it is the app's own table, sitting where only the script path reaches. The same-server rationale in §3.2 is about the **ELT staging table**, whose rows are copied into the target — it does not extend to the manifest, which is never copied anywhere. **The cheap resolution is to split them: raw ELT staging in `LOSS` (where the copy needs it), manifest state in `WORKBENCH` (where the app's other state lives), joined by analysis + perspective.** That preserves the entire argument Nagi accepted, because the large-volume same-server move is the ELT, not the manifest.
**Note that code already leads here**, as `23` O23-2 warned: `db/elt.py` implements `upload_parquet` and `enrich` via a session-scoped temp table (PR #91, `b883116`). A session-scoped temp table is not a persistent staging table in `LOSS`, so **the primitives exist but not the arrangement today approved** — write the DDL and the worker against the decision, not against the primitive.

3. **What is the grain?** §9 keys results on (analysis | rdm) × `perspective_code`. Ben's manifest is per-download-archive, and one archive returns **one Parquet file per perspective** (`22` **D28**) — so one archive is *several* perspectives. Fix the grain explicitly, because it decides whether the load ID in **O25-2** is per-archive or per-perspective, and it is `21` **O21-7**'s unresolved `result_export` grain question arriving from the other end.

**Whatever is decided, `result_export` (§9) and `delivery_kind`'s `sql` seed finally have a concrete referent.** `location` is documented as "file path (Parquet) or SQL ref (Loss Repo / RDM)"; the SQL ref is now three named tables in `CRE Trial ELT Repository`. Record which, and note that one export produces both a file location and a SQL location — the point `21` **O21-7** raised and `22` **O22-10(c)** repeated.

### 3.4 Reconciliation — **O25-2** (the load ID)

Nagi asked for one and Ben agreed. The Workbench already has it: §8's `rwb_job.id`, with `UNIQUE(requestor_type, requestor_id, rwb_job_type)` as the dedup key and a documented claim/heartbeat/chain lifecycle. So the decision is narrow and specific:

- **Do the `LOSS` staging tables carry `rwb_job_id`?** It would be a cross-database reference with **no FK** — the same shape §8 already accepts for `rwb_job.requestor_id` ("no DB FK; target varies by type"), so there is precedent.
- **Or does the load ID belong to the manifest table, generated per load?** Which is only coherent once **O25-1** decides where the manifest lives.
- Either way, **Nagi's stated purpose is operational**: "what happened and when." Whichever ID lands in `LOSS` must be resolvable by a CIC DBA with no Workbench access — which argues for a value that is meaningful on its own (a timestamped batch key) rather than only a Workbench GUID.

### 4.2 Why this is not settled

**The two decisions of September 2 agree; the model does not.**

- **`24` O24-10** retired `22` **D29**'s pre-fetch that same morning: retrieval is **lazy, at export submission**. The strongest argument for holding Parquet on disk — having it ready so an on-demand validation does not wait — is therefore gone, and it went before this call, not after it.
- **Today's D6** deletes the archive after staging, on disk-pressure grounds that are real: `22` **O22-10(a)** already flagged the storage question at "100+ analyses × several perspectives."
- **§9** still models `elt_file_path`, `ep_file_path`, `plt_file_path` and `stats_file_path` as **stored relative paths** under `{submission_outputs_dir}/{analysis_id}/{perspective_code}/{result_type}.parquet` (and an RDM-keyed path for broker results). **Paths that are deleted after staging are lineage pointing at nothing.**

So this is a documentation correction rather than a design conflict — but it is not a mechanical one, because §9's paths were carrying a real idea. **Two readings survive, and they differ in what lineage means.** Either the paths become **historical record** (where the file *was*, for audit, accepting that it is gone) — cheap, and honest about a transient artifact; or the *downloaded archive* is transient while a **Workbench-written Parquet is retained** as the durable per-perspective artifact, in which case §9's paths keep their current meaning and something has to write that file. The second reading is the one `22` **O22-11** quietly assumed when it planned to "update the Parquet file itself with a new column" for event type — **and today's D3 makes that plan redundant, because enrichment is now a SQL join in the staging table.** Pick a reading and say which; the enrichment location follows from it. → **O25-3**.

Note the second-order effect if the transient reading wins outright: **the enriched Parquet is where `22` O22-11's event-type column was going to live** ("update the Parquet file itself with a new column"). If the Parquet does not survive the load, the enrichment has to happen in the staging table instead — which is, conveniently, exactly what today's D3 SQL-join design does. **These two designs are alternatives, not layers.** Pick one, and record which.
