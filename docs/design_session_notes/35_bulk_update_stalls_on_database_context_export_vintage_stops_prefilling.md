## 2. The bulk update, demoed (D1, D3, D4)

**The setup.** Ben's local databases mirror CIC's: the Workbench database, and the loss database with CIC's `dbo` tables plus the Workbench-owned `stage` schema. *"I added a CRM contract status table… I can, of course, change the name of it and change its shape."* Cheryl: *"It'll be a view, so we can call it whatever we want."* That's `2d9bf3e`'s `dbo.CRMContractStatus (CRMID NVARCHAR(50) PK, Status NVARCHAR(50))` in `db/bootstrap/loss_dev_mirror.sql`, seeded by `make seed-demo` with one row per contract (a third carrying a different status) plus ten CRM-only IDs.

**The run.** Three CRM IDs set to Lost in the table, then the dry run. **The first execution failed**:

> **Ben:** *"Ohh no, I have a something wrong with it. Contract status… Check status. Okay. Contact status kind of it lives and exists correctly."* → **Cheryl:** *"If to set what database you're pointing to."* → **Ben:** *"I suppose that I do. Let's put this in the lost database then. Or, let's put this in the work done statements."* → **Wendy:** *"Old eagle eye, Cheryl."* → **Ben:** *"Probably, probably should account for that somehow."*

The rerun showed the summary (source rows, to update, already at status, not in Workbench, unknown, duplicates, dry run), the problem list and the change list, and then applied the changes live. Asked what "issues" it reports, Ben checked offline and named *"an invalid status in the source table"* and *"CRM ID listed more than once"*. **That's `:75-80` exactly.**

**⚑ Why it failed, and the two-line fix.** The script is a single batch with unqualified Workbench names (`contract_status_kind`, `contract`, `submission`) and one three-part source name. **Its header states the precondition (`:3`, *"CIC runs this in SQL against rwb_workbench"*) and nothing checks it.** In SSMS the database is whatever the query window last used, which is easily the loss repository if you've just been looking at the source table, as Ben had. Add, after `SET XACT_ABORT ON`:

```sql
IF OBJECT_ID('dbo.contract_status_kind') IS NULL
BEGIN
    RAISERROR ('Run this script in the Workbench database (the one holding contract_status_kind).', 16, 1);
    RETURN;
END;
```

## 3. The matched-contract row (D2)

**The demo.** Ben: *"I did do one ask, which was, let's update the contract fields based on the contracts we're actually getting back from the query, which was pretty easy to do because we're already joining with this contract table."* Search one CRM ID and you get that CRM ID, its treaty type and its inception. Search the "0000" CRM ID and you get *"the correct inception date for that CRM ID."* Search two CRM IDs and *"I'm just getting the data back for these that are the contracts that I'm actually receiving."* Cheryl: *"Very nice… That's great."*

**What `2a84778` built** (`submission_service.py:487-530`, `017` T084–T086):

- `_contract_clauses(filters)` is lifted out of `submission_filter_clauses`, so the list's `EXISTS` and the row summary use **the same clauses**. P-18 guarantees one contract meets them all together.
- `_attach_contracts` appends those clauses to its per-page contract read, orders by `inserted_at, id`, and takes **the first** for all three columns. The other matches go behind "+N more" (CRM ID) and the other distinct types in kind-table order (treaty type).
- `row.latest_inception_date` becomes `row.inception_date`. `_FIRST_INCEPTION` (a capped one-row subquery, `row_limit(1)`) replaces `_LATEST_INCEPTION` as the default and Inception sort key.
- Tests: the same deal filtered by CRM ID, contract status, treaty type + status, in force and inception, checking all three columns each time (`test_submission_service.py`).

**So `34`'s central defect is gone**: a row can no longer show one contract's CRM ID beside another's inception. **And the rule was told to the client, which `017` T087 asked for**: *"Inception date is going to show me in this row, first contract entered… When I enter a single CRM ID, these three fields are contract fields."* The first clean statement of this column in four sessions.

**⚑ The residual: sort vs display under a filter.** `_FIRST_INCEPTION` (`:438-440`):

```python
"COALESCE((SELECT c.inception_date FROM contract c "
"WHERE c.submission_id = s.id ORDER BY c.inserted_at, c.id {cap}), s.inserted_at)"
```

It has no contract clauses. **So with, for example, an inception-date filter matching a submission's second contract, the row shows the second contract's date and the page is ordered by the first contract's.** The comment above it says *"It is the date the row shows, so the list is ordered by what the analyst reads."* That's true only unfiltered. P-17 says the same (*"The default sort is that same inception descending"*), and so does `2a84778`'s message. **Ben's closing line on the demo slipped the same way**: *"Inception dates always going to be the first entered contract on the submission"*. That's right unfiltered, wrong with a filter, where the code correctly shows the first *matched*.

**How much it matters: little.** With an inception filter every returned row shows the same date, so the sort order among them is arbitrary anyway. With a CRM-ID filter it's usually one row. It bites with a contract-status or treaty-type filter across many multi-contract submissions. **Two ways out, pick one:** (a) format the same clauses into the subquery (`WHERE c.submission_id = s.id AND <contract_clauses>`), which is straightforward since the clauses are already bound for the `EXISTS`; or (b) leave it and add *"under a contract filter the sort stays on the first-entered contract"* to P-17 and the comment. **Either way, change P-17's approval source from "user 2026-09-24" to "note 35 D2".** → **O35-2**.
