## 2. The current export process, end to end

The artifact **O20-13** asked for. Reproduced in sequence because the Workbench flow has to answer each step.

1. **Attach to the server** where the RiskLink data lives, go to **results data transfer**, type any part of the database name (it highlights multiples if there are any), select it.
2. **The tool lists every analysis run in that database.** Cheryl picked earthquake results to upload.
3. **Metadata gate.** Nothing proceeds until the analyst fills the metadata block: "there's still some manual data entry on the part of the analyst." Fields: **client ID** (searchable, creatable), **treaty year** (short dropdown — "you rarely need to go backwards"), **treaty inception date**, **data vintage**, **financial perspective** (pre-cat net, gross, post-cat, RP, ground up, treaty/TY), **in-force date**.
4. **Select analyses** — and, for the treaty case, specific **treaties** within them (§7).
5. **Review.** A table showing a placeholder data ID, analysis ID, analysis name, description, currency, **AAL**, plus two integrity checks: **events with loss greater than exposure** and **events not in the catalog** (§8). Cheryl: "We get a chance to review the results, which is very, very handy."
6. **Commit,** with an opt-in checkbox for writing historical events to their own table. Writes three tables (§9). Cheryl: "you'll notice this checkbox came on."

**Ben's own restatement of the Workbench requirement**, given verbatim near the end and worth keeping as the acceptance list: "We need to be able to **pick multiple analyses** … **provide a specific perspective that's valid across all of these analyses** … be able to **search that client list by name** and choose a client ID and a client name … **review and versus commit**."

**Caveat on capture — `O20-13` is only half closed.** The walkthrough happened; it was **not captured**. `18` **O18-12** established that CIC artifacts are the highest-value input on this project (Cheryl's Excel drove `19` end to end), and `20` O20-13 explicitly asked for screenshots or a recording. The transcript is the only record, and it is lossy in exactly the places that matter — see **O21-12**. → **O21-13**.

## 4. The client table — a second CIC-owned system the Workbench must write (D2–D6)

The first metadata field, and the first genuine schema surprise.

### 4.1 What it is

- **Location:** the **repository database** — the same one holding the loss tables. Ben confirmed: "so being able to read from this specific table and write to it would be possible then, if it's all in the same loss database." Cheryl: "Everything that we're doing is going to be in this particular database today."
- **Shape:** client ID is "simply a running number. It's nothing super fancy" — an auto-incrementing integer, plus a client name and an **Active** flag.
- **Interaction:** search by name (the picker highlights matches), select an existing client, **or create a new one on the fly**. Cheryl: "Say select, it throws it into the client ID, so I don't have to know the client ID."
- **Ownership:** Cheryl was explicit that this is not the Workbench's data — "**I don't think it's anything you have to maintain. I just think it's something you have to be able to access.**"

### 4.2 Client ID is not `cedant_name` (D6)

Ben asked the right question immediately: "We're not storing something called Client anywhere in Workbench right now. We do have ce[dant], right, as a field on the submission. … would that be equivalent? Or is this representing something different?"

Cheryl: "**It is probably the combination of the ceded and the submission type.** … we started by attaching the specific reinsurance type to the client name because it was getting confusing where we had one client that had, we were looking at for four different types of reinsurance. We wanted to have a unique identifier for that."

So the grain differs: §3's `cedant_name` is one string per deal-party; a repository client ID is closer to **(cedant × treaty type)** and is an **external identifier CIC keys on**. Selecting or creating one is not derivable from `cedant_name` + `treaty_type_code` mechanically, because the existing rows are free-text names built by hand over years.

### 4.3 Write semantics, and what Ben asked for

- **The insert statement.** Ben: "still seeing what add new client does under the hood from an insert statement perspective would be useful for me to see" — it "could be as simple as putting in a name … and it's an auto incrementing client ID integer that we don't have to maintain ourselves." Cheryl: "Okay, I can get that to you for sure."
- **Active flag not needed (D5).** Ben asked whether the insert must send it. Cheryl: "I would say you don't need this."
- **Keep the ability to pin an ID (D4).** The tool allows it, and CIC deliberately seeds odd numbers to mark test clients ("we put some of these ones that are like weird like this so that we know they're test"). Ben: "I don't think it's a huge effort to essentially build something similar to this, where you can edit both. And it auto-populates if you're adding a new one." Cheryl treated it as low stakes — a user can insert directly in SQL — "if for some reason that's a sticking point, I don't think I would worry too much about it."

### 4.4 Reconciliation — **O21-1**

§1 names four connections and describes `LOSS` as "App — `db/bootstrap/loss_schema.sql`". `20` **O20-11** already re-framed that as a **dev mirror of a foreign schema**. Today extends the problem in three ways:

1. **The foreign surface is wider than the loss tables.** It now includes a **client table** whose rows the app must **INSERT** into. `bootstrap-loss` must mirror it too, and the drift story O20-11 asked for now covers a table whose *contents* (not just its shape) are operational CIC data.
2. **A write to a foreign table needs a home in the Workbench model.** The selected or newly-created client ID has to be recorded against the export — it is the parameter that makes the pushed rows identifiable. §9's `result_export` holds `delivery_code` and `location` and nothing else. Decide whether the analyst-entered parameter set (client ID, dates, perspective, CRM ID, returned data ID) lives on `result_export` or a new child table; see **O21-2** and **O21-7**, which want the same answer.
3. **`20` O20-12's client-ID gap dissolves rather than closes.** The answer is *not* "add a client ID to `submission`" — the value is chosen per export against a foreign list, and one submission can legitimately push under different client IDs across treaty types. Do **not** model it as a submission attribute. Ben should confirm whether the client search is scoped or filtered by anything (`cedant_name`?) or is a raw name search across the whole table, because that determines whether the export screen can pre-select sensibly.

Note also the constitution angle: Art. 11 governs what the request path may do against a database. A client **search** is a natural request-path action (the analyst types and expects results), and a client **insert** is a state change against a foreign production system. Both need placing deliberately — the export itself is worker-side under Art. 5, but the client picker probably is not.

- **No size, so probe blind:** "**What's also not helpful is that I don't get the size.** So I can't, for any ELT or PLT, know how big it is and how many calls I need to make. So I have to use limit and offset however many times."

- **Cap:** "I can pull a maximum of **1000 rows** every time."

### Reconciliation — **O21-9**

- **§9's `elt_record_count "from get_elt() response"` is wrong.** There is no count in the response. The value is knowable only *after* full pagination (or after a flat-file export). Either re-source the field (populate it after retrieval, as a derived count) or drop it. **FR §7's "ELT summary is shown: AAL, max event loss, record count"** has the same dependency — a record count is not a cheap metric, and neither is a max event loss, which also requires the full ELT. - **`20` O20-15's "lazy/export-triggered" is sharpened, not settled.** Lazy is still right — most of a submission's 4 to 100+ analyses (`05` §7) are never exported. The retrieval is a worker job under Art. 5; the review is a wait. **Decide what the analyst sees while it runs**, and whether the retrieved data is cached against a subsequent commit or re-fetched.

- **Measure a large ELT and a PLT before committing to the API path.** 19 calls is fine; the honest unknown is the distribution, and PLTs are the stated worst case. Rate limits and 30 concurrent users (§1's pooling note) are unquantified.
