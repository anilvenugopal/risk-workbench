Stage schema in the loss repository

The export staging tables live in the loss repository (the LOSS connection), in the stage schema. They are not in the Workbench database, and Alembic does not manage them. A CIC DBA with a db_owner login installs them from db/bootstrap/loss_schema.sql; the Workbench never runs DDL against CIC. Re-running the file is safe. The full definitions are in specs/014-results-export/data-model.md §4.

Three status columns are plain text because they copy Risk Modeler's own values: irp_job.status, irp_edm.status, and irp_rdm.status.

What the rwb_job requestor, link, and context kinds mean is below.

How to change a kind table's values is on page 7.

Submission status is event-sourced. It is the only event-sourced status.

  • submission.status_code holds the current value. New submissions start at ACTIVE.
  • submission_status_event holds every change: submission_id, status_code, reason, at, inserted_by.
  • set_status() in app/services/submission_service.py writes both in one transaction. It opens get_connection("WORKBENCH"), calls conn.begin(), updates submission with WHERE id = :id AND updated_at = :expected, raises ConcurrencyConflict if no row changed, and inserts the event.
  • create_submission() in the same file writes the first ACTIVE event with the submission.

Every other status, including contract.contract_status_code, rwb_job.status_code, and irp_analysis.status_code, is updated in place.

rwb_job: the requestor, link, and context columns

rwb_job holds one row per background job the Workbench runs in a Dramatiq worker (page 2). Each row has three pairs of columns that point at other rows. In each pair, the _type column names the kind of row and the _id column holds that row's id. No _id column has a foreign key, because the table it points into depends on the _type value. Each _type column has a foreign key to its kind table in the list above.

ColumnsAnswersRead by
requestor_type, requestor_idWho or what asked for this job.The unique constraint below. Also the pages that show a job's progress, which find the job by its requestor.
link_type, link_idWhich EDM, RDM, or submission the job belongs to.The RWB Jobs page only.
context_type, context_idWhich row the worker acts on.Nothing.

The unique constraint

rwb_job has one unique constraint, uq_rwb_job_requestor_type, on three columns: requestor_type, requestor_id, and rwb_job_type. One requestor can have at most one row of each job type, for the life of the database. The constraint does not compare input_data, and there is no request hash. Two requests with the same three values are the same job, even if their inputs differ.

Two functions in app/services/rwb_job_service.py insert rows. They differ in what they do when a row with the same three values already exists:

FunctionWhen a row with the same three values existsUsed by
enqueue_rwb_jobInserts nothing and returns None, whatever the existing row's status.The poller and workers, so that a Risk Modeler job seen finishing twice, or a Dramatiq message delivered twice, queues the next job once. Also the analyst actions whose requestor id is new on every click (see below).
ensure_pending_rwb_jobIf the row is succeeded or failed: resets it to pending, adds 1 to attempt_count, replaces input_data, and clears error_detail, output_data, and completed_at. If the row is pending, running, or cancelled: does nothing and returns None.Analyst actions that re-run work on an existing EDM, RDM, portfolio, or analysis, and the Resubmit button on the RWB Jobs page.

A re-run therefore reuses the earlier row. The table keeps only the latest attempt of each job, and the earlier attempt's error_detail is overwritten.

Whether an analyst action creates a new row or reuses one depends on what the code puts in requestor_id:

  • A new UUID on every click: a new row every time. Execute analyses (execute_analysis_batch), group analyses (submit_grouping), and export results (submit_results_export) work this way. An analyst can run the same portfolio and template again while an earlier run is still going.
  • The id of an existing EDM, RDM, or portfolio: the same row every time. Upload, hazard lookup, breakout, and refreshing an EDM's details work this way. A second click while the first job is pending or running does nothing.

link_type values

link_type is edm, rdm, or submission, and link_id is that row's id in irp_edm, irp_rdm, or submission. For an analysis job, the link follows where the analysis came from: its EDM for an analysis the Workbench ran, its RDM for an analysis imported with an RDM, and its submission for a group analysis. not_applicable, with a null link_id, is used by sync_irp_metadata and submit_results_export.

The RWB Jobs page uses the link to show the EDM or RDM name on each row. Its submission search finds a job through the link: directly for submission, and through submission_edm or submission_rdm for edm and rdm. A job with not_applicable never matches a submission search.

context_type values

context_type names the row the worker changes: edm, rdm, portfolio, breakout_group, irp_analysis, execution, or result_export. context_id is that row's id. Both are null for sync_irp_metadata. Every insert writes the pair and Resubmit copies it, but no query reads it.

The context columns came from CR-04c. Its second phase was to move the unique constraint and the page lookups from the requestor columns to the context columns, so that the same work asked for by two different requestors would share one row. That phase was not done. Today one EDM can have two backfill_edm_detail rows: one from an analyst (analyst_request) and one queued after a breakout (rwb_job). edm_service.sync_detail checks both before it queues another.

Data access

All SQL goes through the db/ package. It uses SQLAlchemy Core for connection pools only; there is no ORM. The package is described in db/README.md.

FunctionUse
db.execute(sql, params=None, connection="WORKBENCH")The default. Runs SQL with bound :name parameters and returns list[dict]. Every query that touches a user-supplied value uses it.
db.execute_one, db.execute_scalar, db.execute_command, db.execute_procedureVariants of the same bound-parameter path: one row, one value, one statement that returns a row count, and a stored procedure call.
db.get_connection(name)A context manager that yields a pooled connection. Use it with conn.begin() when two statements must commit together.
db.register_engine(name, engine)Replaces the engine for a connection name. The unit tests use it to point WORKBENCH and LOSS at SQLite.
db.elt.upload_parquetBulk-inserts a Parquet file. The export worker uses it to load stage.rwb_loss_result_elt_data.
from db.scripts import execute_script_fileThe trusted-script path: substitutes {{ param }} into the SQL text, splits on GO, and returns DataFrames. It is not exported from db, so every use is an explicit import. The only caller is infra/scripts/bootstrap_loss.py.

Each connection has its own pool, sized by MSSQL_POOL_SIZE and its siblings, read in db/connection.py. MSSQL_<NAME>_POOL_SIZE and MSSQL_<NAME>_POOL_MAX_OVERFLOW override the two sizing values for one connection. Defaults are on page 7.

Migrations

  • Alembic manages WORKBENCH only. alembic/env.py builds the database URL from the same MSSQL_WORKBENCH_* variables as the app.
  • alembic/env.py has no model metadata, so --autogenerate does not work. Write upgrade() and downgrade() by hand with op.*.
  • alembic/versions/0001_initial.py is the base revision. It is frozen; never edit it.
  • Revision ids are four-digit numbers. The next id is one more than the head that uv run alembic heads shows.
  • Any kind-table rows a change needs go in the same revision as the table or column that uses them.
RevisionChange
0001The full schema and every kind-table seed row.
0002Adds model_profile_irp_id, output_profile_irp_id, and event_rate_scheme_irp_id to analysis_template.
0003Adds irp_job.progress.
0004Adds the cedant table, creating one cedant for each distinct submission.cedant_name. Replaces submission.cedant_name with submission.cedant_id and rebuilds v_contract to join cedant.

tests/iteration1_mirror.py is a SQLite copy of the Workbench schema (ITERATION1_SCHEMA to ITERATION4_SCHEMA) plus the kind-table seed lists (*_SEED). The unit tests build it in memory. A revision that changes a mirrored table or adds a kind-table row must update the mirror in the same commit. tests/sqlserver/test_schema_drift.py compares the mirror's columns with the real schema; it does not check seed rows. tests/loss_mirror.py does the same for the loss database.
