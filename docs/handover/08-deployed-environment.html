8. Deployed environment

The repository describes a RHEL9 deployment and contains the scripts for it. It does not record which servers exist, their hostnames, or what version runs on them. The scripts and runbooks use the account cinreadmd and the app directory /rms, which are the values on the deployed server. Their examples also use the address 172.19.253.47. That is the WSL2 address of the RHEL9 VM used to test the scripts (RHEL9_SSH_KEY_SETUP.md); the deployed environment does not use it.

Outbound connections

Every row below needs a firewall rule that lets the app server reach that host and port. Getting the firewall requests created, approved, and carried out was the biggest blocker in the first deployment. Any new server, for production or a lower environment (B11 on page 9), needs the same rules, so raise the requests as soon as the server's IP address is known.

Data Bridge accepts connections only from IP addresses on its allowlist. Besides the firewall rule, the public IP address that the app server's requests to Data Bridge come from must be added to the Data Bridge allowlist. A new server, or a change to the network address CIC's outbound traffic uses, needs a new entry.

Valkey listens on 127.0.0.1:6379 on the app server and needs no outbound rule. The shared drive is mounted by the operating system, so the app opens no connection to it; the account that runs the app (cinreadmd) has read access, which the import file browser needs. Writing export archives to the shared drive needs write access to their location (B8 on page 9).

Enabling HTTPS

HTTPS is wanted in production (B12 on page 9). Nothing serves it today: site.conf listens on port 80 only, and analysts reach uvicorn over HTTP on port 8000 (B1). The steps below end TLS at nginx on the app server, which is what the repo is built for. Fix B1 first, because the steps change the nginx server block that does not serve today.

  1. Hostname. Choose the DNS name analysts will use and point it at the app server. The certificate, the Entra redirect URI, and the analysts' bookmarks all use this name.
  2. Certificate. CIC issues a certificate for the hostname from a certificate authority the analysts' browsers trust, such as CIC's internal CA. Put the certificate with its full chain, and its private key, on the app server, for example in /etc/pki/tls/certs/ and /etc/pki/tls/private/. Make the private key readable by root only; nginx reads it as root when it starts or reloads. Name who renews the certificate before it expires.
  3. nginx. Change deploy/nginx/site.conf in the repo, not /etc/nginx/conf.d/risk-workbench.conf on the server: rhel9-ssh-deploy.sh rewrites that file from site.conf on every deploy. Add listen 443 ssl, ssl_certificate, and ssl_certificate_key to the server block. Add a server block on port 80 that only redirects: return 301 https://$host$request_uri;. The deploy substitutes only $APP_ROOT, so write the certificate paths as fixed paths or add them to the envsubst call in rhel9-ssh-deploy.sh. deploy/nginx/nginx.conf is for Docker dev and stays on HTTP.
  4. Deploy health check. The last step of rhel9-ssh-deploy.sh runs curl -sf http://127.0.0.1:80/api/health. Once port 80 redirects, curl gets a 301, which -sf counts as success, so the check reports OK with an empty body. Change it to call the HTTPS address.
  5. Inbound firewall. Raise a firewall request for port 443 from the analysts' network to the app server. Raise it early: firewall requests were the biggest blocker in the first deployment (Outbound connections). If firewalld runs on the server, open HTTPS there too: sudo firewall-cmd --permanent --add-service=https, then sudo firewall-cmd --reload.
  6. Close port 8000. Change rhel9-start.sh to start uvicorn with --host 127.0.0.1 instead of 0.0.0.0, so the app cannot be reached over plain HTTP past nginx. nginx already sends requests to 127.0.0.1:8000.
  7. infra/.env. Set APP_ENV=production, which marks the session cookie Secure, so browsers send it over HTTPS only. Set it in the same change as HTTPS: with APP_ENV=production, sign-in over http:// on port 8000 stops working. It also turns off /docs and switches the logs to JSON (page 7). Set ENTRA_REDIRECT_URI=https://<hostname>/auth/callback and register that URI in Entra (Step 7 of docs/ENTRA_SETUP.md). Stop and start the app.
  8. Check. Open https://<hostname>/ in a browser, check the browser trusts the certificate, sign in, and check that http://<hostname>/ redirects to HTTPS.

If CIC ends TLS at a load balancer instead, the certificate and the inbound port 443 rule go on the load balancer. nginx keeps listening on port 80, reachable from the load balancer only, and site.conf needs no TLS block. Steps 1, 6, 7, and 8 still apply.

Deployment process

Today the code is copied onto the server by hand (Manual deployment); no CD process runs the scripts below (B2 on page 9). rhel9-app-install.sh fails at pip install because the server may not connect to PyPI (B3).

Manual deployment

Your own account on the server (for example bbaile4) uploads a zip of the repository. cinreadmd then stops the app, copies the new code into /rms, and starts the app.

  1. On your machine, clone the repository, or pull the latest commit into an existing clone.
  2. Compress the repository folder itself, not its contents, to a zip file such as risk-workbench.zip. Step 9 expects one top-level risk-workbench folder in the zip.
  3. Upload the zip as your own account: scp "C:\path\to\risk-workbench.zip" bbaile4@<host>:/rms.
  4. SSH into the server as your own account and make the zip readable by cinreadmd: chmod 644 /rms/risk-workbench.zip.
  5. Switch to the run account: su cinreadmd.
  6. Stop the app: APP_DIR=/rms bash /rms/infra/scripts/deploy/rhel9-stop.sh.
  7. Create the directory to unzip into: mkdir -p /tmp/risk-workbench-deploy.
  8. Check that cinreadmd can read the zip: unzip -l /rms/risk-workbench.zip lists its files.
  9. Unzip: unzip -o /rms/risk-workbench.zip -d /tmp/risk-workbench-deploy.
  10. Delete the Git history and your local settings file from the unzipped copy: rm -rf /tmp/risk-workbench-deploy/risk-workbench/.git and rm -f /tmp/risk-workbench-deploy/risk-workbench/infra/.env. Deleting infra/.env keeps the next step from overwriting the server's /rms/infra/.env.
  11. Copy the new code over the app directory: cp -a /tmp/risk-workbench-deploy/risk-workbench/. /rms/.
  12. Apply the Alembic revisions. The server has no uv, so source infra/.env and run Alembic from .venv, as rhel9-app-install.sh does: cd /rms && set -a && source infra/.env && set +a && .venv/bin/alembic upgrade head.
  13. Start the app: APP_DIR=/rms bash /rms/infra/scripts/deploy/rhel9-start.sh, then check curl -s http://127.0.0.1:8000/api/health.
  14. Clean up: rm -rf /tmp/risk-workbench-deploy and rm /rms/risk-workbench.zip.

These steps do not run rhel9-app-install.sh, so they install no package from requirements.txt. cp -a deletes nothing: a file removed from the repository stays in /rms. It also copies every file in the zip, gitignored or not, so zip a checkout with no .venv, or it overwrites files in /rms/.venv. rhel9-stop.sh interrupts any running job; the poller resets it to pending after the start.

One-time setup, on the server:

  1. DEPLOY_USER=<account> APP_DIR=/rms bash rhel9-setup.sh (needs sudo). Installs git, Python 3.14, ODBC Driver 18, nginx, Valkey, gcc, gettext, and rsync; creates the app directory and /var/lib/risk-workbench/valkey; enables nginx; writes two sudoers rules for the deployment account (systemctl reload nginx, and tee /etc/nginx/conf.d/risk-workbench.conf); sets vm.overcommit_memory=1.
  2. Install the deploy SSH key for the deployment account.
  3. Place /rms/infra/.env by hand. No script creates or overwrites it.
  4. Create the three databases. rhel9-app-install.sh does not create them. To confirm: who creates the Workbench database at CIC and with which login.

Each deployment:

  1. On the server, make sure no job is in flight: APP_DIR=/rms bash infra/scripts/deploy/rhel9-drain-check.sh while the workers are still running, or check Workflows → RWB Jobs.
  2. On the server, as the run account, stop the app: APP_DIR=/rms bash infra/scripts/deploy/rhel9-stop.sh.
  3. From a developer machine or CI runner with the code checked out: DEPLOY_HOST=<user>@<host> DEPLOY_DIR=/rms SSH_KEY=<key> bash infra/scripts/deploy/rhel9-ssh-deploy.sh.
  4. On the server, as the run account, start the app: APP_DIR=/rms bash infra/scripts/deploy/rhel9-start.sh, then check /api/health and rhel9-worker-health.sh.

rhel9-ssh-deploy.sh runs these steps over SSH and stops at the first failure:

  1. Checks that infra/.env exists on the server.
  2. Pushes the code with rsync --delete-after --filter=':- .gitignore', so gitignored files such as infra/.env and .venv are never sent or deleted.
  3. Runs rhel9-check-prereqs.sh.
  4. Runs rhel9-drain-check.sh: waits until rwb_job has no pending or running rows, checking every DRAIN_POLL_INTERVAL_SECS (default 5) for up to DRAIN_TIMEOUT_SECS (default 300).
  5. Runs rhel9-app-install.sh: builds .venv, installs requirements.txt with pip install --require-hashes, runs alembic upgrade head, and checks the ODBC driver and app import.
  6. Writes site.conf into /etc/nginx/conf.d/risk-workbench.conf with APP_ROOT filled in, and reloads nginx.
  7. Calls http://127.0.0.1:80/api/health.

Two things to know about this order. The code is already replaced by the time the drain check runs. And the drain check runs after the workers are stopped, so any pending row left at stop time can never clear and the deploy stops at the timeout. That is why step 1 of each deployment drains first. The deploy does not restart the app; the health check at the end reports the old processes or none.

The pull-based alternative, run on the server, is APP_DIR=/rms BRANCH=<branch> bash infra/scripts/deploy/rhel9-pull-code.sh (it refuses if the checkout has local changes unless given --stash or --force), then rhel9-app-install.sh. It needs GitHub access from the server.
