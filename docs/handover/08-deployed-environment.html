8. Deployed environment

The repository describes a RHEL9 deployment and contains the scripts for it. It does not record which servers exist, their hostnames, or what version runs on them. The scripts and runbooks use the account cinreadmd and the app directory /rms, which are the values on the deployed server. Their examples also use the address 172.19.253.47. That is the WSL2 address of the RHEL9 VM used to test the scripts (RHEL9_SSH_KEY_SETUP.md); the deployed environment does not use it.

Deployment process

Today the code is copied onto the server by hand; no CD process runs the scripts below (B2 on page 9). rhel9-app-install.sh fails at pip install because the server may not connect to PyPI (B3).

The runbooks are in docs/RHEL9/:

One-time setup, on the server:

  1. DEPLOY_USER=<account> APP_DIR=/rms bash rhel9-setup.sh (needs sudo). Installs git, Python 3.14, ODBC Driver 18, nginx, Valkey, gcc, gettext, and rsync; creates the app directory and /var/lib/risk-workbench/valkey; enables nginx; writes two sudoers rules for the deployment account (systemctl reload nginx, and tee /etc/nginx/conf.d/risk-workbench.conf); sets vm.overcommit_memory=1.
  2. Install the deploy SSH key for the deployment account.
  3. Place /rms/infra/.env by hand. No script creates or overwrites it.
  4. Create the three databases. rhel9-app-install.sh does not create them. To confirm: who creates the Workbench database at CIC and with which login.

Each deployment:

  1. On the server, make sure no job is in flight: APP_DIR=/rms bash infra/scripts/rhel9/rhel9-drain-check.sh while the workers are still running, or check Workflows → RWB Jobs.
  2. On the server, stop the app: APP_DIR=/rms bash infra/scripts/rhel9/rhel9-stop.sh.
  3. From a developer machine or CI runner with the code checked out: DEPLOY_HOST=<user>@<host> DEPLOY_DIR=/rms SSH_KEY=<key> bash infra/scripts/rhel9/rhel9-ssh-deploy.sh.
  4. On the server, start the app: APP_DIR=/rms bash infra/scripts/rhel9/rhel9-start.sh, then check /api/health and rhel9-worker-health.sh.

rhel9-ssh-deploy.sh runs these steps over SSH and stops at the first failure:

  1. Checks that infra/.env exists on the server.
  2. Pushes the code with rsync --delete-after --filter=':- .gitignore', so gitignored files such as infra/.env and .venv are never sent or deleted.
  3. Runs rhel9-check-prereqs.sh.
  4. Runs rhel9-drain-check.sh: waits until rwb_job has no pending or running rows, checking every DRAIN_POLL_INTERVAL_SECS (default 5) for up to DRAIN_TIMEOUT_SECS (default 300).
  5. Runs rhel9-app-install.sh: builds .venv, installs requirements.txt with pip install --require-hashes, runs alembic upgrade head, and checks the ODBC driver and app import.
  6. Writes site.conf into /etc/nginx/conf.d/risk-workbench.conf with APP_ROOT filled in, and reloads nginx.
  7. Calls http://127.0.0.1:80/api/health.

Two things to know about this order. The code is already replaced by the time the drain check runs. And the drain check runs after the workers are stopped, so any pending row left at stop time can never clear and the deploy stops at the timeout. That is why step 1 of each deployment drains first. The deploy does not restart the app; the health check at the end reports the old processes or none.

The pull-based alternative, run on the server, is APP_DIR=/rms BRANCH=<branch> bash infra/scripts/rhel9/rhel9-pull-code.sh (it refuses if the checkout has local changes unless given --stash or --force), then rhel9-app-install.sh. It needs GitHub access from the server.

Operations runbook

Run every command on the app server, from the app directory, as the deployment account.

TaskSteps
StartAPP_DIR=/rms bash infra/scripts/rhel9/rhel9-start.sh. Starts Valkey, uvicorn, one worker per queue, and the poller, in that order. It refuses if port 8000 is in use, so stop first if anything is running. nginx is not touched.
StopAPP_DIR=/rms bash infra/scripts/rhel9/rhel9-stop.sh. Stops uvicorn, every worker, the poller, then Valkey. It waits 35 seconds per process; a worker still finishing a job after that is reported, not killed. Jobs it interrupts are reset to pending by the poller after the next start.
Restart after an infra/.env changeStop, then start. There is no script to restart a single process.
A dead workerRun APP_DIR=/rms bash infra/scripts/rhel9/rhel9-worker-health.sh. Read /var/lib/risk-workbench/worker-<queue>.log for the cause. Then stop and start. The poller resets that queue's interrupted job to pending once its heartbeat is older than RWB_HEARTBEAT_STALE_SECS, and the new worker picks it up.
A stuck rwb_jobFind it on Workflows → RWB Jobs. Dead (no heartbeat): it is reset automatically once its queue has a live worker. pending and never picked up: that queue's worker is not running. running with a live heartbeat: it ends at its Dramatiq time limit; if it must end sooner, kill that queue's worker (PID in /var/lib/risk-workbench/pids/worker-<queue>.pid), then start it again. failed: Resubmit on the page. See page 2.
A stuck irp_jobThe poller checks it on every pass until Risk Modeler reports a final status; Workflows → IRP Jobs shows the status Risk Modeler returns. There is no action in the Workbench to cancel it. Check the job in Risk Modeler. A failed analysis submission is retried automatically, then the analysis shows as error.
