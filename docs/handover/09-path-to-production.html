9. Path to production

The state of the deployed environment is as the development team reported it on 2026-10-01. Every claim about the code was checked against it on the same day. The Owner column is for the handover call.

The existing server stays as the lower environment, and the app runs there with every item on this page open. CIC is building the production server now (deployment checklist on page 10). Do the three items in Before production before analysts rely on the production server for real work. Schedule the items in Production cleanup after go-live.

Before production

#ItemState todayWhat is neededOwner
C1Production needs CIC's real loss repositoryOn the existing server, the LOSS connection points at CRE_Trial_ELT_Repository, a trial repository, not CIC's real loss repository. dbo.Client and dbo.Lookup_RMS_HistoricalRDS in it were loaded by hand.Set MSSQL_LOSS_* in the production server's infra/.env to the production loss repository. A CIC DBA installs db/bootstrap/loss_schema.sql in it. Run specs/014-results-export/cic-reference/validate_loss_repo_server.sql against it.
C2nginx does not serve the app on port 80On the existing server the app cannot be reached through nginx on port 80. The cause has not been investigated. uvicorn listens on 0.0.0.0:8000, so the app can be reached on port 8000 without nginx. The last step of rhel9-ssh-deploy.sh calls http://127.0.0.1:80/api/health, so it fails while nginx is broken.Decide whether production uses nginx. If it does, find and fix the cause. HTTPS (C3) ends TLS at nginx, so it depends on the answer.
C3HTTPSAnalysts reach uvicorn over plain HTTP on port 8000 (C2) and sign in with a Workbench username and password. The password and the session cookie cross CIC's network unencrypted. APP_ENV must stay development while the app is on HTTP: APP_ENV=production marks the session cookie Secure, browsers then do not send it over HTTP, and sign-in fails.The steps in Enabling HTTPS on page 8: a hostname and certificate, a TLS server block in site.conf, an inbound firewall rule for port 443, uvicorn bound to 127.0.0.1, and APP_ENV=production. Depends on C2. If CIC decides plain HTTP is acceptable on its internal network, CIC's security team accepts that risk in writing instead.

Production cleanup

#ItemState todayWhat is neededOwner
C4Deployment is manualThe code is copied onto the server by hand (Manual deployment on page 8). No CD process runs. The scripts exist: rhel9-ssh-deploy.sh pushes the code with rsync over SSH, rhel9-pull-code.sh pulls it from GitHub on the server, and rhel9-app-install.sh installs it. See page 8.CIC builds the CD process, and it can call these scripts. The push needs SSH from the CD runner to the server; the pull needs GitHub access from the server.
C5The server cannot reach PyPIrhel9-app-install.sh downloads every package in requirements.txt from PyPI, which the server may not connect to. The first install ran with a firewall rule opened for the install and closed after it. A changed package is copied to the server as a wheel by hand (RHEL9_QUICKSTART.md, section 2).CIC hosts the Python packages in a CIC-owned Artifactory. Then point pip on the server at it, with PIP_INDEX_URL or /etc/pip.conf; the install script sets no index of its own. The hashes in requirements.txt still check every package, so the Artifactory must serve the same files as PyPI.
C6The shared drive is mounted at the wrong levelThe shared drive is mounted on the server at /Workbench. The team wants a higher-level directory mounted.CIC mounts the higher-level directory on the server. Then set SHARED_DRIVE_ROOT in infra/.env to the new mount point, and stop and start the app.
C7Logs are not collected or rotatedEach process writes its log to /var/lib/risk-workbench/ on the server, and nothing picks them up. rhel9-start.sh appends to each log with >>, so a restart keeps the lines that show why a process died (fixed in issue #173). Nothing rotates the logs, so they grow until someone truncates them. See page 7.Add log rotation. Ship the logs to a log aggregator, following CIC's standard approach. LOG_FORMAT=json writes one JSON object per line.
C8Entra sign-in is not set upAnalysts sign in with a Workbench username and password (AUTH_MODE=password), which is the production sign-in for v1. Entra sign-in is optional. POST /auth/login in app/routers/auth.py accepts a password whatever AUTH_MODE is set to; AUTH_MODE=oidc only hides the form.Register the app in Entra and set the ENTRA_* variables, following docs/ENTRA_SETUP.md. Entra accepts an http redirect URI only for localhost, so this needs HTTPS (C3). To turn password sign-in off, make POST /auth/login refuse when AUTH_MODE=oidc, then set AUTH_MODE=oidc.
C9Export archives are not written to the shared driveEach export keeps the Risk Modeler archive under EXPORT_ARCHIVE_DIR and unzips it into EXPORT_STAGING_DIR, both set in infra/.env. The app never creates either directory; the stage step fails an analysis when one is missing. cinreadmd has read access to the shared drive only, so the archives cannot be written there today.Archives are written to a location on the mounted shared drive, still to be chosen; it may sit under the higher-level mount in C6. CIC creates that directory and gives cinreadmd, the account that runs the app, write access to it. Then set EXPORT_ARCHIVE_DIR in infra/.env to that directory, and stop and start the app. EXPORT_STAGING_DIR stays a local directory on the app server, emptied after each analysis. Nothing deletes archives; sweep-export-archives.sh runs only by hand (runbook on page 8). If CIC sets a retention period, schedule the sweep; an archive is the only copy of the original ExpValue and StdDev of the rows the load procedure corrects.
C10The app does not start after a server restartrhel9-start.sh starts uvicorn, the Dramatiq workers, the poller, and Valkey with nohup. Nothing starts them after a reboot or restarts one that dies. Only nginx is a systemd service. The team decided not to write systemd units for the other four.Give the team that maintains and restarts the Linux server rhel9-start.sh and the "After a server restart" steps in the runbook on page 8. That team runs the steps after every restart.
C11One account deploys the code and runs the appcinreadmd owns /rms, deploys the code, and runs the app. Every script takes one account, DEPLOY_USER.Split the account in two. The deployment account owns /rms, runs rhel9-app-install.sh, holds the two nginx sudoers rules, and reads infra/.env, because the drain check and the migrations connect to the Workbench database. The run account runs rhel9-start.sh and rhel9-stop.sh, owns /var/lib/risk-workbench/, reads /rms and infra/.env, and has the shared drive access in Accounts on page 10. Make infra/.env readable by these two accounts only. Infra creates the accounts. rhel9-setup.sh gives DEPLOY_USER both /rms and /var/lib/risk-workbench, so it needs a second account setting for the run account.
