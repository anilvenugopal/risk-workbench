Dependencies

  • Python 3.12 or later (requires-python in pyproject.toml). The Docker image uses Python 3.12 on Debian 12 with ODBC Driver 18.
  • pyproject.toml lists the runtime packages. Dependency groups add dev (pytest, pytest-asyncio, pytest-cov, httpx, ruff, debugpy) and one group per irp-integration source (irp-pypi, irp-testpypi, irp-local). default-groups selects dev and irp-pypi.
  • uv.lock pins every resolved version. Install with uv sync.
  • Upgrade one package at a time with uv sync --upgrade-package <name>.
  • uv is a developer tool only. The RHEL9 server has no uv.

requirements.txt is generated from uv.lock for the server:

  1. bash infra/scripts/generate-requirements.sh runs uv export --frozen --no-dev and writes requirements.txt: hashed pins, no dev tools, first line -e ..
  2. Commit it with the dependency change. bash infra/scripts/generate-requirements.sh --check fails if it is out of date. CI does not run the check.
  3. On the server, infra/scripts/rhel9/rhel9-app-install.sh removes the -e . line and runs pip install --require-hashes, then installs the project itself.

AI tooling

The project was built with Claude Code and SpecKit. Neither is needed to run or change the code.

  • AGENTS.md holds the instructions every coding agent follows. CLAUDE.md points Claude Code to it.
  • .claude/settings.json sets includeCoAuthoredBy: false, so Claude Code adds no attribution to commits.
  • .claude/skills/ holds the SpecKit commands. .specify/ holds SpecKit's templates, scripts, and the constitution.
  • docs/agents/issue-tracker.md says issues live in GitHub Issues and are handled with the gh CLI. docs/agents/domain.md describes the optional CONTEXT.md and docs/adr/, which do not exist yet.

Decision history

To find out why something works the way it does, look in this order:

WhereWhat it records
specs/<feature>/spec.md and plan.mdThe decision tables: P-nn product decisions, T-nn technical decisions, O-nn open items, each with a status.

docs/design_session_notes/Numbered notes from each design session with CIC (01 to 35). Decisions are tagged D<n> and open items O<note>-<n>; specs cite them as "note 32 D17".
docs/CR/Change requests that changed the architecture. completed/ holds CR-01 (the rwb_job queue), CR-02 (no workflow engine), and CR-03 (the submission model). CR-04 split the workers into one queue per job type.

UI workflow

  • For a screen with new layout, build a rendered HTML preview first and get it approved, then build the Jinja2 template and route.
  • Start the preview by copying docs/ui_previews/_scaffold.html, which inlines the app's real design tokens and components. Reuse the app's existing classes; show the empty and error states as well as the normal one.
  • Skip the preview for copy changes or a field added to an existing component.
  • Build one user story at a time, end to end, then stop so the approver can click through the running feature.

The full rules are in docs/UI_WORKFLOW.md; the previews already made are in docs/ui_previews/.
