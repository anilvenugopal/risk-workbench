7. Configuration and observability

Settings the functional team will ask about

Analysts and CIC's modeling leads will ask for changes to the settings below. There are three ways a setting is changed: an env var in infra/.env, a new Alembic revision for a kind table, or the admin screen.

a. Changed in infra/.env, then restart

Every process reads its settings once, at start. After editing infra/.env, restart each process the table names. The processes are uvicorn (the "app"), the Dramatiq workers, and the poller; how to restart them is on page 8. Restarting all of them is always safe.

b. Changed by a new Alembic revision

These value lists are kind tables. There is no admin screen for them. Each change is a new Alembic revision, reviewed and deployed like code.

  1. Create the revision: uv run alembic revision -m "<what changes>" --rev-id <next id>.
  2. In upgrade(), use op.execute() to INSERT the new row, or UPDATE its label or sort_order. In downgrade(), undo it.
  3. Add or change the same row in the matching *_SEED list in tests/iteration1_mirror.py.
  4. Run uv run pytest tests/unit, then deploy. The deploy runs alembic upgrade head.

The full revision rules (Migrations) and the codes each table holds today (Workbench schema) are on page 3.

Users with the admin role see Administration in the rail, at /admin/users (app/routers/admin.py). Every action takes effect on the user's next request; no restart.

Logging

  • All three processes configure logging with setup_logging() in app/logging_setup.py: uvicorn in app/main.py, each worker in app/workers/entrypoint.py, and the poller in app/poller/run.py.
  • Every log line, including uvicorn, Dramatiq, and SQLAlchemy lines, goes to stderr through one handler.
  • LOG_LEVEL sets the level: DEBUG, INFO, WARNING, or ERROR (default INFO).
  • LOG_FORMAT sets the format: console for readable lines, json for one JSON object per line, or empty to pick by APP_ENV (json in production, console otherwise).

app/log_context.py adds context fields to every line in a chain of work:

  • Each HTTP request gets a correlation_id, taken from an incoming X-Request-ID header or newly generated, and sent back in the X-Request-ID response header. The request middleware writes one access line per request with method, path, status, and duration; /static/ is skipped.
  • A worker job adds rwb_job_id, rwb_job_type, and worker_id.
  • The poller adds irp_job_id.
  • rwb_job.correlation_id and irp_job.correlation_id store the id of the request that started the work, so you can search all three processes' logs for one id to follow an analyst's click through its jobs.

Health and monitoring

CheckWhat it tells you
GET /api/healthJSON with db_workbench, db_exposure, db_loss (each ok or an error), redis, and env. No sign-in needed. It always returns HTTP 200 and "status": "ok", even when a check fails, so read the individual fields. It does not check the workers, the poller, Risk Modeler, or DATABRIDGE.
make wsl-worker-health; infra/scripts/deploy/rhel9-worker-health.sh [--queue q]For every queue, whether its PID file points at a live process, and a separate process scan. Exits 0 if any queue is alive, 1 if none is.
infra/scripts/deploy/rhel9-drain-check.shWaits until no rwb_job row is pending or running. See page 8.
Workflows → RWB Jobs, /workflows/rwb-jobsThe 50 most recent rwb_job rows, filterable by submission, owner (defaults to you), job type, and status. A running row with no recent heartbeat shows as dead ("worker stopped heartbeating"). Cancel works on pending, failed, or dead rows; Resubmit works on failed rows and reuses the same row. A live running job cannot be stopped from the page. Any signed-in user can use it.
Workflows → IRP Jobs, /workflows/irp-jobsThe 50 most recent irp_job rows: type, entity, Risk Modeler status, progress, submitter, attempts. Read-only.

The Active, Review Queue, and Exceptions pages under Workflows are empty placeholders.

There is no alerting. Nothing pages anyone when a worker dies or exports fail.
