Request path vs. worker path

A route handler answers the analyst within one HTTP request. Anything slow, anything that waits on Risk Modeler, and anything whose size grows with the book runs in a worker or the poller.

 request path (uvicorn)            worker path (Dramatiq)             poller
 ----------------------            ----------------------             ------
 validate the form                 claim the rwb_job row              one get_*_job call per
 read and write rwb_workbench      submit the Risk Modeler job        in-flight irp_job
 enqueue rwb_job + send message -> record irp_job                     on a terminal status:
                                   read results, DATABRIDGE,            update the entity,
                                   download and load exports            enqueue the next rwb_job
May run in a route handlerMust run in a worker or the poller
  • Reads and writes on rwb_workbench through db.execute().
  • Reading dbo.Client and the historical event lookup, and inserting an export's manifest rows, in the loss database.
  • Creating an rwb_job row and sending its Dramatiq message.
  • Risk Modeler name searches for the as-you-type name checks (app/services/name_check.py), and the EDM search on the Sync from Risk Modeler page.
  • One-analysis reads that answer a check the analyst is waiting on, such as the analysis import check (get_analysis_metadata).
  • The grouping inspection (grouping.inspect) and analysis delete.
  • One single-row DATABRIDGE count, the breakout match count. It must fail open.
  • Every Risk Modeler job submission: imports, analyses, GeoHaz, grouping, exports, and portfolio creation.
  • Every job status check (poller only).
  • Result retrieval: EP, statistics, and treaties.
  • Every other DATABRIDGE read.
  • Downloading, staging, and loading exports.
  • poll_*_to_completion methods are never called anywhere.

Article 11 of the constitution allows synchronous job submission on the request path. The code does not use that today: every submit runs in a worker, and the poller resubmits failed analysis jobs.

Job lifecycle

Two tables track background work. They have no foreign key between them.

TableTracksStatus column and values
rwb_jobWork the Workbench runs itself in a Dramatiq worker. Unique on (requestor_type, requestor_id, rwb_job_type), so enqueuing the same work twice creates one row.status_code, a key into rwb_job_status_kind: pending, running, succeeded, failed, cancelled
irp_jobOne Risk Modeler job. irp_id is Risk Modeler's job id. irp_job_type is one of import_edm, import_rdm, geohaz, analysis, grouping, export.status, plain text copied from Risk Modeler (for example QUEUED, FINISHED, FAILED, CANCELLED), plus the app's own SUBMISSION FAILED and SUBMISSION RETRYING

An rwb_job row moves through these steps:

  1. A route, a worker, or the poller inserts it as pending and sends a Dramatiq message.
  2. A worker claims it with UPDATE ... SET status_code='running' WHERE status_code='pending' and stamps claimed_by with hostname:pid.
  3. While the job runs, a thread writes rwb_job_heartbeat.heartbeat_at every RWB_HEARTBEAT_INTERVAL_SECS (default 30).
  4. The worker sets succeeded or failed, with error_detail on failure. Dramatiq never retries an actor (max_retries=0).

Each poller pass, every POLL_INTERVAL_SECS (default 15), runs five steps in order:

  1. For each in-flight irp_job, one status call to Risk Modeler. On a terminal status it updates the entity and enqueues the next rwb_job (for example finalize_analysis after an analysis, stage_results_export after an export).
  2. Reconciler: resets running rows whose heartbeat is older than RWB_HEARTBEAT_STALE_SECS (default 120) back to pending.
  3. Sends a Dramatiq message for every pending row, which recovers a lost message.
  4. Returns SUBMISSION RETRYING rows untouched for IRP_SUBMISSION_RETRY_STALE_SECS (default 300) to SUBMISSION FAILED.
  5. Submission retry: resubmits the newest SUBMISSION FAILED analysis job of each analysis, after IRP_SUBMISSION_RETRY_BASE_SECS × 2attempts seconds, up to IRP_SUBMISSION_MAX_RETRIES attempts (defaults 60 and 3). Only analysis jobs are retried. When attempts run out, the analysis is set to error.

A job that looks stuck is one of three cases:

CaseWhat happens
The worker process died.The heartbeat goes stale and the reconciler resets the row to pending. No action is needed if that queue has a running worker.
The job is blocked inside a call.Dramatiq's time limit fails the row: 10 minutes by default, 1 hour for execute_analysis_batch and run_breakout_*, 6 hours for stage_results_export and load_results_export. A call blocked inside C code ignores the limit; kill that queue's worker process.
The row is pending and nothing picks it up.No worker is running for that queue. Start it.

Analysts can cancel or resubmit an rwb_job on the RWB Jobs page; see page 7. The operator steps are on page 8.

Architecture rules

The binding rules are the 13 articles of .specify/memory/constitution.md (v4.3.0). /speckit-analyze treats a violation of any article as critical.

ArticleRule in one line
1The navigation manifest, app/nav/manifest.py, is the one place that defines pages, the rail, the sidebar, breadcrumbs, and search.
2What the analyst can do next is computed in code; EDMs, portfolios, analyses, and treaties are looked up in Risk Modeler by name, and profiles and event rate schemes by Risk Modeler id.
3Internal categorical values are rows in *_kind tables; only external status mirrors and the stage schema in CIC's database may use plain text.
4submission.status_code is event-sourced through submission_status_event; every other status is updated in place.
5A mechanical follow-up step runs automatically; a step that needs judgment waits for the analyst's click.
6There is no row-level security; roles gate functions, not rows.
7All SQL goes through the db/ package: bound parameters through db.execute(), and a separately imported trusted-script path.
8Pages are rendered on the server with FastAPI, Jinja2, and HTMX; Alpine.js only for small client behaviour.
9Styling extends the ITCSS design system through named tokens, with no hard-coded colours.
10The rwb_job table is the queue; each job type has its own Dramatiq queue, and the heartbeat reconciler stays.
11Risk Modeler polling and result work runs only in the poller and workers; DATABRIDGE is read only through irp-integration.
12Behaviour is tested in three tiers: unit, SQL Server, and Risk Modeler sandbox.
13Sign-in is Entra ID with a password fallback; the session cookie holds only the session id; every state-changing request carries a CSRF token.

Where the code departs from these rules today is listed under known debt on page 9.
