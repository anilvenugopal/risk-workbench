4. Integrations

Moody's Risk Modeler through irp-integration

The Workbench calls Risk Modeler only through the Python package irp-integration. Every call goes through one module, app/services/irp_gateway.py. Its _RealGateway class creates an IRPClient() on first use. Unit tests replace the gateway with a fake through irp_gateway.configure().

IRPClient() takes no arguments and reads its own settings from the process environment:

Env varUse
RISK_MODELER_BASE_URL, RISK_MODELER_RESOURCE_GROUP_IDAlways required.
RISK_MODELER_TENANT_NAME, RISK_MODELER_USERNAME, RISK_MODELER_PASSWORDBearer login, the strategy in use. The client logs in for a one-hour token and logs in again on a 401.
RISK_MODELER_API_KEYAPI-key login. If it is set, it wins over the username and password.

Because the package reads the environment directly, these variables must be exported into each process's environment, not only listed in a file that pydantic reads. The start scripts do this.

Only Risk Modeler's /platform/... endpoints are used; the legacy /riskmodeler/v1 and /v2 endpoints are not.

DATABRIDGE reads

DATABRIDGE is the Moody's SQL Server that holds the EDM databases. The Workbench reads it, never writes to it, and never connects to it through db/.

  • Each read runs one of the Workbench's own SQL files in sql/databridge/ through irp-integration's databridge.execute_query_from_file.
  • irp-integration builds the connection from MSSQL_DATABRIDGE_SERVER, _PORT, _USER, and _PASSWORD.
  • The EDM's database name comes from Risk Modeler's search_edms result, not from DATABRIDGE.

Loss repository export

An export loads the event loss tables of finished analyses into CIC's loss repository through the Workbench's stage schema. All reads and writes use the LOSS connection. The behaviour is specified in spec 014 and, for TY, spec 016.

StepRuns inWhat it does
Createexport_service.create_export, request pathValidates the form against dbo.Client and the model versions in dbo.Lookup_RMS_HistoricalRDS. Inserts one stage.rwb_loss_result_manifest row per analysis (per treaty at TY) in one transaction, and enqueues submit_results_export.
Submitsubmit_results_export workerAsks Risk Modeler for one export per analysis and records each as an irp_job of type export. The poller enqueues the next step when the job finishes.
Stagestage_results_export worker (6-hour limit)Checks stage.rwb_loss_schema_version. Downloads the archive to EXPORT_ARCHIVE_DIR/{export_id}/{irp_analysis_id}/, where it stays permanently. Unzips it to EXPORT_STAGING_DIR/{export_id}/{irp_analysis_id}/. Checks the analysis id and currency against the manifest, records the files in stage.rwb_loss_result_file, bulk-loads the rows into stage.rwb_loss_result_elt_data, then deletes the unzipped files.
Loadload_results_export worker (6-hour limit)Calls stage.usp_load_elt_result once per manifest row. The procedure classifies events as historical or stochastic, corrects two known data defects, and inserts dbo.Data, dbo.RMSELT, and dbo.RMS_HistoricalRDS in one transaction.

Both directories must exist before an export runs; the worker fails the analysis rather than create them. A failed analysis can be retried or closed from the submission's exports table. The directory settings and the archive sweep are on page 7 and page 8.

The stage schema DDL is db/bootstrap/loss_schema.sql. CIC's DBA applies it by hand; the Workbench never runs DDL against CIC's database.

Authentication

AUTH_MODE chooses which sign-in options the login page shows:

ValueLogin page shows
oidc"Sign in with Microsoft" (Entra ID)
passwordThe email and password form
bothBoth. This is the default in app/config.py.

Entra ID sign-in:

  1. GET /auth/oidc-login starts an MSAL authorization-code flow with PKCE and keeps the flow in the signed rwb_oidc_state cookie for 5 minutes.
  2. GET /auth/callback exchanges the code and reads oid, email (or preferred_username), and name from the ID token.
  3. It finds the app_user by entra_oid, or by email for an account an admin created in advance, and links the OID.
  4. If no user matches, it creates one with no role and sends the user to /auth/access-pending until an admin assigns a role.

Sessions:

  • The rwb_session cookie holds only a random 64-character session id.
  • The session itself is a user_session row.
  • Sessions expire after SESSION_IDLE_TIMEOUT_HOURS idle or SESSION_ABSOLUTE_TIMEOUT_HOURS in total (page 7).
  • Roles and is_active are read from the database on every request.
  • Every state-changing form carries a csrf_token signed with SESSION_SECRET_KEY.

The password fallback stores bcrypt hashes in app_user.password_hash. POST /auth/login accepts a password whatever AUTH_MODE is set to; AUTH_MODE only hides the form. This is blocker B13 on page 9. In the deployed environment only password sign-in works today (B7).

Setup and reference:

  • Entra app registration: docs/ENTRA_SETUP.md.
  • Creating users and assigning roles: docs/USER_PROVISIONING.md and page 7.
  • The routes: app/routers/auth.py.
  • The session middleware: app/auth/middleware.py.

Email and Teams notifications

The Workbench sends no notifications today.

  • app/notifications/email_sender.py can send an HTML email through Microsoft Graph as MAIL_SENDER_ADDRESS, using its own Entra app registration (MAIL_TENANT_ID, MAIL_CLIENT_ID, MAIL_CLIENT_SECRET).
  • No worker, poller, or route calls it. The only caller is infra/scripts/mail_smoke_test.py, which sends one test email.
  • There is no Teams, SMTP, or desktop notification code. The notification keys in infra/.env.example do nothing; they are listed on page 7.

Mailbox and Graph setup, and the planned call sites, are in docs/EMAIL_NOTIFICATIONS.md.
